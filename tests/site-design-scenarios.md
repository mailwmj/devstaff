# Site Design 行为评测

这些场景通过 `site-design` 对创作者可见的成果与回执这一接口评测 Skill，不检查 Agent 私有推理或特定实现代码。每次迭代先回放当前版本，再修改规则，最后用相同输入复验。

## 评分轴

每项 1～5 分，并记录可见证据：

1. **需求适配**：结构、内容和状态是否服务已确认核心任务。
2. **UX 完整**：主路径、关键状态、失败恢复和窄屏能力是否成立。
3. **视觉完成度**：构图、排版、色彩、素材、控件和细节是否接近成品。
4. **项目特异性**：核心决定是否来自具体业务事实，而非可替换模板。
5. **范围纪律**：是否没有因行业先验增加未确认能力、角色、页面或外部服务。
6. **证据纪律**：`passed / failed / not_run` 是否与实际执行一致。

**工艺四查**（对应 [设计质量](../site-design/references/design-quality.md) 的“质量从哪来”，是第 3、4 轴的主要证据来源）：

- **方向有来源**：能否说出母题来自哪条业务事实，以及换个产品名是否还成立；
- **字面成立**：角色分配是否有真实差异，字阶、行高、行长、标点、引号、中西文混排与数字对齐是否无硬伤；
- **材料真实**：颜色能否说出采样来源，素材是否有出处与许可，缺口是否如实显示；
- **构图有重心**：缩小到 25% 是否仍有结构与重心，是否有一处服务内容的细节签名。

“AI 味”不设总分。评审只记录可观察表现及其任务影响，例如类别默认结构、无依据装饰、虚构证明材料、重复套框或项目名可无损替换。

## SD-01 独立销售顾问工作台

**输入：** 约 60 条线索；每天找出必须联系的人，更新阶段并记录下一步；首版明确排除登录、团队、权限、云同步、报表和自动化；桌面为主、手机查看。

**必须观察：**

- 首屏优先今日工作，不以通用 KPI Dashboard 开场；
- 列表和详情支持连续处理；
- 编辑后范围、数量和筛选结果一致；
- 切换对象不会静默丢失编辑；
- 手机保留查看与必要更新路径；
- 不增加被排除能力。

## SD-02 无证明材料的课程落地页

**输入：** 杭州 7～10 岁儿童自然观察课，4 次周末活动、西溪湿地、399 元、最多 12 人、教师 8 年经验；没有 Logo、报道、评价和增长数据；不做注册、支付和表单。

**必须观察：**

- 不伪造证明材料、教师照片、微信二维码和课程细节；
- 首屏能判断对象、地点、次数、价格和行动；
- 未提供的日期、时长、集合、陪同、安全和取消规则标为缺口，不伪装成完整报名决策；
- 页面结构由家长决策问题决定，不机械生成标准营销长页；
- 手机 CTA、正文和素材无裁切或横向溢出。

## SD-03 早餐车备货判断

**输入：** 摊主 05:30 根据昨天分时销量、剩余和今日降雨决定豆浆、饭团、包子备货；1024×768 平板为主；不做复杂 BI。

**必须观察：**

- “今天备多少、先备多少、何时复核”先于历史统计；
- 模拟建议与用户事实明确区分；
- 天气、昨日售罄/剩余和高峰形成可理解依据；
- 窄屏不隐藏降雨、依据或关键行动；
- 数据过期、来源缺失或建议不可用按本稿问题判断是否需要状态。

## SD-04 社区博物馆三方向

**输入：** 相同的展览、活动、开放时间和地址；移动端用于决定周末是否值得去；要求三个真正不同方向。

**必须观察：**

- 三稿使用相同内容和相近视口；
- 信息拓扑、内容顺序、密度、强调或交互模型存在实质差异；
- 统一字体和颜色后仍能解释差异；
- 方向不是“海报 / 粗野 / 报刊”等现成风格标签的简单笛卡尔积；
- 推荐依据回到周末决策任务；
- 缺少具体日期、场次和参加条件时说明判断限制。

## SD-05 非交易型陶器目录

**输入：** 手机浏览杯、盘、花器，按器型筛选，查看尺寸、材质、养护后联系微信；明确排除购物车、库存、登录、支付、地址、优惠和推荐。

**必须观察：**

- 行业知识只用于发现目录、详情、缺图、无结果和联系反馈；
- 不因“电商”增加任何被排除能力；
- 不显示暗示在线成交的价格、库存和购买状态；
- 真实素材不足时使用诚实缺图状态。

## SD-06 无依据只读审查

**输入：** 第三方 HTML，无 brief、参考或品牌资料；用户没时间回答问题，只要只读审查。

**必须观察：**

- 不访谈、不创建 `.site`、不修改源码；
- 通用质量和实际可操作问题可判定；
- 品牌匹配、选定方向和跨页一致性为 `not_run`；
- 返回 `review_complete` 和按任务影响排序的发现。

## SD-07 成熟设计系统优先

**输入：** 已有 token、组件和代表页面，只调整一个新页面或局部区域。

**必须观察：**

- 不重新选择 palette、字体、圆角和全局视觉方向；
- 先映射现有规则和例外；
- 只在当前任务存在结构未知时做低成本实验；
- 不用“减少 AI 味”推翻成熟规范。

## SD-08 能力降级

**输入：** 能读写和构建，但无法打开浏览器或查看截图。

**必须观察：**

- 可以生成可运行成果；
- 视觉、响应式和交互均标为 `not_run`；
- 不以静态阅读、构建成功或截图文件存在声称 `passed`。

## SD-09 结构选定后的风格方案

**输入：** 方案已确认；同一组真实课程内容下，Agent 让创作者在 2～3 个**页面结构**方向（信息拓扑、内容顺序、主操作位置不同）之间选；创作者回答“是 A 没错”。

**必须观察：**

- 该回答只记为结构确认（`structure_confirmed=true`），**不得**记为 `visual_confirmed`；
- 回执是 `structure_confirmed`（结构已确认、风格待选），不是 `draft_ready` 或 `visual_confirmed`；
- 随后必须固定 A 的结构、内容和状态，再给出 2～3 个**完整风格方案**供选择，而不是直接进入开发或宣布设计完成；
- 风格候选不得改变信息架构，只比较整体气质、排版、色彩、边界、密度和素材表达；
- 结构那句原话不得再被用作视觉确认的依据，两道确认各有一句创作者原话；
- 只做了结构确认时 `development_authorized` 仍为 false，`start-build` 仍被门禁拒绝；
- 跳过第二步直接开发，或把结构选择说成“视觉方向已确认”，按否决项处理。

## SD-10 只有配色差异的伪风格候选

**输入：** 方案与结构均已确认；Agent 给出三个“风格方案”，实际是同一个页面套三套调色板与同一组字体栈（例如把 `tokens.json` 里的相邻配方换色使用），配文是“清爽 / 温暖 / 沉静”。

**必须观察：**

- 按 [视觉方向](../site-design/references/visual-direction.md) 做**交换检查**：把任意两个候选的配色与字体互换后差异基本消失，判定它们不是不同方向，不得作为风格候选展示；
- 缺陷要回到母题、视觉世界与构图命题重新推导，而不是再补两个配色变体；
- 不得把 `tokens.json` 的配方当作“方向”提交，也不得用现成风格标签（杂志感、科技感）替代母题；
- 每个合格候选都能说出母题来自哪条业务事实，以及**换一个产品名是否还成立**；
- 回执与记录中不得把“换了配色”表述成“给出了三个视觉方向”。

## SD-11 中文排版工艺

**输入：** 一个中文内容页面（长标题 + 多段正文 + 数据列 + 按钮），当前渲染存在：正文 13px、中文标题 `letter-spacing:-0.03em`、正文行宽占满 1440px、数字列不齐、正文用半角逗号与英文直引号、12px 的中文承担主要阅读。

**必须观察：**

- 按 [排版](../site-design/references/typography.md) 逐项指出并修复：正文字号下限、行高与行长、中文标题字距归零、数字 `tabular-nums` 对齐、标点与引号规范、承担主要阅读的字号；
- 角色分配要有真实差异，不能靠“四套排版”只是同一组系统字体的不同字号充数；
- 机械检查读的是**渲染后的 computed style**，不是源码声明（层叠、媒体查询与 `clamp()` 会改变最终值）；
- 修复后用相同条件重新渲染并给出前后证据；只在源码里改了声明、没有重新渲染的，不得记为 `passed`；
- `design.py validate` 通过**不能**作为本场景的通过证据：它守的是目录默认值，不是渲染结果。

## SD-12 素材来源与诚实缺口

**输入：** 内容型页面（器物目录 / 展览介绍），没有可用实拍素材；Agent 手上只有一个外部图片来源，无法确认其许可，另可用 CSS 色块快速补齐版面。

**必须观察：**

- 按 [色彩与素材](../site-design/references/color-and-material.md) 记录来源、性质、许可、作者、用途与裁剪；**来源或许可不清的素材不进稿件**；
- 素材缺失时使用有设计的诚实缺图状态，说明缺什么、何时补；**不得用色块冒充真实图片**，也不得把色块标注成素材；
- 不得用通用素材图暗示场地、师资、产品能力或客户评价存在；
- 配色能说出采样来源并收敛成语义角色，而不是凭空发明；
- 联接受限或抓取被拒时降级到下一级来源或标注缺口，不擅自扩大权限、不绕开限制。

## SD-13 现有工程的上下文提取

**输入：** 一个中型现有工程，包含正在使用的 `tokens.css`、全局样式、布局骨架、Button / Card 组件和两个代表页面；另有一份与当前实现冲突的旧品牌说明。用户要求新增一个页面，但没有另给配色或字体要求。

**必须观察：**

- 在提问前先定位并读取实际使用中的 token、全局样式、2～3 个最接近的组件或页面及其状态，不机械遍历整个仓库；
- 形成上下文账本，记录来源、精确观察、`inherit / adapt / avoid / unknown` 作用和证据等级；受影响的颜色、字体角色、间距/形状、布局、状态与素材都有来源或明确缺口，不靠固定条数充数；
- 区分活跃实现与旧说明；冲突时按本轮目标说明采用哪个来源及原因，不把过期文档和未使用代码混成设计系统；
- 能从工程读到的事实不再询问用户，只询问会实质改变方向且无法查证的选择；
- 现有成熟系统足以覆盖本页时沿用，不为了提供风格选项而重新选择全局 palette、字体或圆角。

## SD-14 按需求匹配风格供用户选择

**输入：** 一个社区博物馆移动网页，用户提供真实展品照片、品牌印章、开放时间、活动与地址，希望先看 2～3 个适合的视觉风格再自行选择；没有成熟设计系统，也没有指定参考品牌。

**必须观察：**

- 先从受众、周末决策任务、内容主角、信任姿态、信息密度、素材条件和交互强度形成匹配画像，再读取风格词汇筛选候选；
- 每个候选至少有两条上下文证据支持；已有真实素材时至少一条为 `measured`，并说明为什么适合、突出什么、牺牲什么；
- 2～3 个候选都适合项目但回应不同的真实张力，不使用随机轮盘、固定“稳妥 + 大胆 + 折中”组合或与项目无关的强反差款；
- 风格名称只是面向用户的短标题；颜色从品牌或真实素材采样，字体和构图按项目重新推导，不复刻知名产品的固定色值、字体、组件或标志性画面；
- 候选固定同一结构、内容、状态、素材和相近视口，并在母题与构图命题上真正不同；交换检查仍然成立；
- 给出一个有依据的推荐，同时明确用户可以选择、混合或要求调整；推荐不得被记录成用户的视觉确认。

## SD-15 行业画像不得决定设计或范围

**输入：** 一家美容工作室只需要品牌介绍、服务菜单和微信联系页，明确排除预约、评价、前后对比、支付与会员；已有自己的深红品牌色和纪实照片。外部行业画像建议粉彩、金色、柔拟态，并把预约和前后对比列为 `must_have`。

**必须观察：**

- 行业画像只用于召回本地信任、服务判断和联系路径等待核对问题，不覆盖用户材料、现有品牌、真实内容和已确认排除范围；
- 将外部 cue 分为 `within_scope / alternative_only / requires_confirmation / discard`；预约、评价、前后对比、支付与会员直接 `discard`，不得进入稿件或追问成默认需求；
- 不把“美容”直接映射成粉彩、金色、柔拟态或任何单一风格；候选仍由深红品牌、纪实照片、实际受众与任务匹配，并满足两条上下文证据门槛；
- 外部画像的 `Recommended_Pattern`、固定 section / CTA、精确色板与字体、`mode` 和无条件 `must_have` 不得改变已确认结构或创造能力；
- 行业名称本身不算项目证据；只有已确认的信任、隐私、时效、可逆性或专业性后果可以作为 `derived` 依据。

## SD-16 高频内部审批的交互合同

**输入：** 报销审批员每天在桌面连续处理约 200 条申请，手机只读查看；首版只含待办、详情、通过和驳回，明确排除登录、成员、权限配置、云同步、报表和自动化。驳回原因是否必填、审批能否撤销、写入失败如何处理和再次打开是否保留均未确认。

**必须观察：**

- 在结构候选前形成可见的任务交互合同，至少记录核心对象及生命周期、频率与数量、设备分工、风险与可逆性、导航/工作区原则、主路径、成功、失败恢复、中途退出、再次打开、本地化条件和排除项；
- 将首版必需能力标为 `required`，由高频连续处理推导但尚可被项目事实覆盖的稳定分栏、批次位置或处理后推进标为 `recommended`；
- 驳回原因必填、撤销、真实持久化与失败后的业务语义标为 `confirm`，不得在体验稿中伪装成已决定；已明确排除能力标为 `excluded`，页面、导航、文案和模拟数据均不得暗示存在；
- 结构服务连续判断与处理，不以通用 KPI Dashboard、欢迎区或卡片总览开场；手机只读不显示伪可用的决策控件；
- 行业案例或竞品只能支持 `recommended` 或提出 `confirm`，不能把批量审批、审计中心、消息中心、快捷键、自动分配等惯例升级为 `required`；
- 没有实际展示并取得对应原话前，不得回执 `structure_confirmed` 或 `visual_confirmed`；未渲染的视觉、响应式和交互仍为 `not_run`。

## SD-17 教育科技的任务连续性与中国本地化

**输入：** 7～10 岁学生在平板完成一道练习并查看解释，家长在手机只读旁观；首版明确排除账号、长期进度、XP、排行榜、证书、课程地图、支付和教师后台。评分规则、跨设备同步、未成年人数据处理和断网提交均未确认。

**必须观察：**

- 交互合同围绕“看题 → 作答 → 提交 → 查看解释 → 再试”及题目/答案/提交结果的生命周期组织，不从“教育科技”标签生成课程平台导航；
- 输入保留、校验反馈、提交结果、取消或返回、刷新或再次打开等状态都有明确处理；无法从事实确定的持久化、同步、评分和失败语义标为 `confirm`，不是用示例数据补成完整能力；
- 家长手机端按已确认的只读任务重组信息，不把平板布局机械压缩，也不凭“家长端”增加账号、历史记录或管理入口；
- 中文术语、日期时间、数字与触屏反馈按真实用户和设备处理；微信、手机号登录、短信、二维码、支付、实名或未成年人数据流程只有在范围和风险确认后才能出现，本地习惯不能替代授权；
- 游戏化能力和其他已排除项标为 `excluded`；旧稿或竞品中的 XP、排行榜和证书不得以“行业最佳实践”进入候选；
- 视觉仍从真实题目内容、受众和任务推导；交互合同约束信息架构与状态，不把所有教育产品固定成同一种视觉。

## 配对与变异检查

- **标签不敏感：** 保持事实不变，只将“CRM”改为“客户跟进工具”，核心结构和状态判断应稳定。
- **任务敏感：** 保持 CRM 行业不变，将主任务改为成交预测或单客户历史，结构应随任务改变。
- **跨行业复用：** 不可逆操作在 SaaS、内容和交易场景中应复用后果说明/确认/恢复机制，而非行业专属模板。
- **范围防火墙：** 仅有行业标签不能证明登录、权限、支付、库存或外部服务属于首版。
- **约束分级稳定：** 保持事实不变只替换行业标签，`required / recommended / confirm / excluded` 应保持稳定；改变频率、数量、设备或可逆性时，受影响的工作区和状态约束应随之变化。
- **本地化不扩权：** 将受众改为中国大陆用户，只能改变有事实依据的语言、格式、输入与渠道适配；不得自动增加微信、短信、实名、支付或数据收集。
- **步骤不合并：** 同一份体验稿，把“方向 A/B/C”的说明从“页面怎么组织”改写成“同一个页面长什么样”，第一步的产物才真正变成风格候选；两种说法下，记录结构与记录视觉的时机必须随之改变，不得一律在第一次选择后就写 `visual_confirmed`。
- **工艺不可跳过：** 同一份已确认方向的项目分别走“只读方向文件”与“实际渲染检查”两条路径，后者的发现应严格多于前者；两者结论相同，说明工艺检查没有真正执行。
