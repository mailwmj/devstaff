# 运行、依赖与正式实施

## 1. 先检查环境

检测宿主、操作系统、现有运行时和项目原生启动方式，不假定 Python、Node.js、npm、Docker 或浏览器已安装。已有工程沿用其工具链，不运行初始化覆盖。

权限分两类：

- **可自主处理**：项目目录内的 npm/pip 等依赖、项目虚拟环境、开发服务器、非破坏性的端口调整、构建和测试。
- **不可逆动作**：安装系统级 Node.js/Docker/数据库/浏览器，管理员权限，修改系统环境变量，影响其他项目的全局包或服务，付费/云资源，第三方登录、密钥、域名，公开部署，以及真实敏感数据（个人信息、儿童数据、客户数据）。这些按下节处理。

说明时使用结果语言，例如安装内容、磁盘/系统影响、是否常驻和用户需完成的动作，不把命令本身当解释。Agent 能解决的普通报错不推给非技术用户。

## 1b. 不可逆动作按宿主能力分档

上面那张不可逆清单**不写进状态机**，也不靠 Agent 的自觉。它靠宿主已有的权限边界——那是唯一"由别人维护、Agent 无法伪造"的通道。能力分三档，**先探测再依赖，不得假定有某一档**：

| 档 | 宿主的形态 | Agent 该做什么 |
| --- | --- | --- |
| **T1 审批提示** | 执行前弹出确认，由人裁决（GUI 点击、终端确认、approval prompt 等，形态各异） | 直接发起该动作，让宿主的审批通道接管；不自己再造一套确认 |
| **T2 沙箱边界** | 项目目录可写，其余只读，越界即被拒 | 越界动作必然被拒，据此向用户说明"这需要你授权"，不要尝试绕过沙箱 |
| **T3 无边界也无提示** | 无沙箱、无审批，Agent 有大范围权限 | 唯一防线是**停下来问并等回答**：说清动作、影响和不可逆之处，得到明确答复才继续 |

**档位不同，纪律相同：不可逆动作在得到人的明确答复前不执行。** 差别只在"由谁强制"——T1/T2 由宿主的机制强制，T3 只有 Agent 自律加用户可核对的说明。

因此有两条硬要求：

1. **先探测，再声明。** 不确定宿主属于哪一档时，按 T3 处理（最保守），并在交付说明里如实写明本轮实际是哪一档。**不能因为宿主是 T1 就省掉说明，也不能在 T3 假装有 T1 的保证。**
2. **T3 下必须逐条回答，不能默认同意。** "你看着办"这类全权委托**不覆盖**不可逆清单；沉默、未回复或有歧义都不算授权。

宿主能力无法探测时，按 T3 执行并如实记录，不写成"已由宿主拦截"。

**这类动作故意不记进 `.site/state.json`。** 它们是动作授权，不是阶段跃迁；把动作塞进阶段状态机会让机制取代目标本身。可逆决定（方案、页面结构、视觉风格、开发授权）走 `site-brief` 的确认记录，不可逆动作走这里，两者不混。

## 2. 选择运行方式

技术栈服从已确认范围，不强制零依赖或双击 HTML。展示页可保持静态；复杂交互可选择合适框架；需要可靠长期或共享数据时使用合适服务与数据库，而不是强行塞进浏览器存储。

新建项目也可在方案和开发授权明确后使用随包 starter：

```text
python3 /absolute/site-builder/scripts/site.py init /absolute/project --template static --title 名称
python3 /absolute/site-builder/scripts/site.py init /absolute/project --template tool --title 名称
python3 /absolute/project/.site/preview.py
```

Python 工具要求 3.10+；Windows 可能使用 `py -3`，Mac/Linux 通常使用 `python3`，以实际检测为准。starter 只接受空目录或仅含 `.site` 记录的目录；后者保留原 brief/state，并在输出中标明是否需要由 `site-brief` 记录推荐 runtime。空目录会创建 `discovering` 默认状态，调用者必须立即把本轮已经获得的方案、页面结构、视觉风格和开发授权交给 `site-brief` 恢复后，才能进入 `building`；只选定结构而还没做风格方案时，恢复后仍停在 `visual_drafting`。starter 只是启动基础，不是视觉体验稿或用户项目完成品。

`site-builder` 的随包预览只服务项目 `web/`，默认回环地址和端口 8765，不是生产服务器。它只证明开发环境正常，不证明接收者能打开。用户目标含分享时，按 `plan-delivery` 选择文件、URL 或安装形态，并在目标渠道实测；不要把单文件 HTML 在聊天工具中的兼容性当作常识。端口占用时不杀无关进程；浏览器存储已绑定旧网址时，先确认旧入口或导出迁移。

## 3. 启动与检查交接

启动后检查实际就绪、入口可达且对应正确项目。脚本文件存在不等于已验证跨平台双击；最终提供当前环境实测的再次启动方式。离开会话后仍需启动进程时，要清楚说明。

体验稿和正式站必须使用不同端口，并各自登记 `owner / PID / 端口 / 服务根目录`。需要交接给独立检查时，先停止自有的体验稿和开发服务，再执行门禁工具的 `handoff`：

```text
python3 /absolute/site-brief/scripts/state.py handoff /absolute/PROJECT \
  --stopped-pid 1234 --freed-port 4174 \
  --service-json '{"owner":"正式站","pid":5678,"port":4175,"root":"/absolute/PROJECT"}'
```

工具会拒绝仍在运行的 PID 和被未登记服务占用的端口，并把当时源码的冻结指纹写进状态；正式服务必须登记在项目根目录之内，避免地址仍指向体验稿目录。交接后任何源码修改都会让 `start-verify` 失败，必须重新交接。不使用“杀掉所有 Node”一类命令管理进程，也不复用归属未确认的端口。

更新使用说明为真实业务和实际命令，并说明数据位置、备份恢复与已知限制。实现完成后把真实入口、启动命令、数据位置和本轮范围交给 `site-check`；不要用开发服务器当次可用代替其再次打开检查。不默认生成 `acceptance-guide.md`。可向用户提议生成本地轻量运行脚本或离线便携包，但必须获得明确确认才写入，不默认做决定。

默认不公开端口、上传数据或创建云服务。用户要求部署或分享时读 publish.md；公开部署、新增费用、账号授权和数据迁移都属于 1b 的不可逆动作，按宿主能力分档处理。

无执行能力时仍可交付文件和准确命令，但必须明确哪些运行、交互和视觉没有实际验证。
