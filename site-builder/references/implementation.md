# 按可体验切片实施

## 输入

正式开发只综合：`.site/brief.md`、`.site/design/packet.json`、选中体验稿、用户反馈、源码和项目原生约定。DesignPacket 的 `gaps` 必须为空；已确认信息不重新访谈。新冲突会改变任务/风险或必须缩减范围时才暂停。

## 纵向切片

每条切片贯穿数据、规则、界面和检查，完成后可以独立体验。第一条沿约定分发渠道打通核心任务，不按“先数据、再接口、最后页面”横向铺开。已交付切片作为不可侵犯的回归不变量（Regression Invariants），后续切片实施必须保持历史切片绿灯。

```markdown
## 切片：<用户获得的能力>
前提：
操作：
可观察结果：
失败恢复 / 中途退出 / 再次打开：
适用状态：
任务合同：<required / recommended / confirm / excluded ID>
设计落实：<direction / grammar / patterns>
检查：<命令、浏览器任务、视口>
```

一个简单项目可以只有一条。`required` 必须实现；`recommended` 采用或记录项目事实支持的偏离；`confirm` 未决定前不实现；`excluded` 不得进入导航、控件、文案、数据或占位状态。

## 微调快道

纯文案修饰、局部字号/间距/色温微调且不改变数据结构、状态机和拓扑结构时走微调快道：就地在已确认规范下修改，做针对性自检后交付，不重置全局大门禁。一旦涉及字段变更、新增页面、状态机分支或不可逆动作，坚决阻断快道并退回完整流程。

## 使用模板

模板是 patterns，不是产品蓝图：

1. `site.py inspect-template <id>` 只读取语义选中的一个模板卡片；
2. 确认 reject conditions 不触发；
3. 复制代码，替换业务字段、真实内容和 grammar；
4. 删除范围外页面、控件、状态和模拟数据；
5. 在 surface brief 记录 selected/adaptations/rejected；
6. 执行模板和项目原生验证命令。

`static / browse / form / tool` 分别覆盖内容阅读、筛选比较、表单恢复和本地 CRUD。它们节省 HTML/CSS/JS 接线 token，但不允许跳过 direction 或确认。无匹配时直接按项目结构实现。

## 原型交接

默认 `evolve`：保留确认过的结构、样式和交互，替换模拟数据、补正式边界、删除候选切换器。只有技术形态无法承载正式要求时 `rebuild`，并记录选中稿、正式入口、保留/替换/删除项和具体原因。`site-check` 用 `prototype_lineage` 复核。

## 状态与数据

只实现任务真实需要的状态：集合考虑空/无结果；异步考虑加载/超时/重试；表单考虑校验、提交中、防重复和失败保留输入；可变内容考虑零值、长文字和缺图；写入、导入和破坏性操作考虑确认、失败与恢复。

数据使用稳定 ID 和单一事实来源。浏览器存储只保证当前设备、浏览器和网址；跨设备/多人目标必须使用已确认的相应方案。导入先校验和预览，失败不覆盖原数据。

## 视觉落实

- direction 的母题、构图和项目签名要出现在核心任务，不只首页首屏；
- grammar 在同角色控件、默认/焦点/禁用/加载/成功/错误状态和跨页面中一致；
- patterns 的每项 adaptation 可以在代码和验证证据中定位；
- 桌面与 390px 都保留核心信息和操作；
- 动效解释状态变化并尊重 `prefers-reduced-motion`。

## 行为反馈

业务规则、状态转换、持久化、导入导出和 Bug 优先用公开行为建立会失败的检查：明确前提/操作/结果 → 观察失败 → 最小实现 → 原生命令与真实浏览器复验。纯内容或视觉变化使用构建和真实渲染，不强制虚假的单元测试。

## 跨平台测试套件与辅助脚本生成规范

创作者与执行环境可能是 **Windows（PowerShell / CMD）** 或 **macOS / Linux（Bash / Zsh）**。

在终端内联拼接脚本存在严重缺陷：
- **PowerShell** 下的反引号（`` ` ``）转义、单双引号嵌套解析以及变量插值机制极其繁琐脆弱；
- **CMD** 缺乏可靠的多行文本输入能力，且特殊符号（`^`、`%`、`&`）限制极多；
- **Bash / Zsh** 下的单双引号冲突与 `<< 'EOF'` 变量展开陷阱极易造成脚本内容损坏；
- 命令行重定向管道极易引入跨平台行尾换行符混乱（CRLF vs LF），进而破坏源码与证据哈希计算。

**Positive Target（正向规范）：**
当需要生成 `.site/checks/verify_suite.py`、自测脚本或辅助工具时，**必须统一调用环境提供的 `write_to_file` 工具直接创建文件**，严禁在 Shell 命令行中通过重定向（如 `cat << EOF`、`echo ... >`）或字符串管道拼接生成多行脚本。这确保了脚本内容、编码格式与换行符在各操作系统下绝对精确与可复现。

切片完成不等于交付；最终仍由冻结后的 `site-check` 独立验证。
