# 渐进式建站

用户只需描述目标和反馈。此 Skill 负责自然语言路由、两个确认门禁、全部正式源码修改、实施、修复和交付；首版梳理、可见实验与独立检查由其他 Skill 负责。

## 执行

1. **识别请求和工程。** 定位用户指定项目，读取源码、原生说明及已有 `.site` 记录；有 `.site` 时先用门禁工具的 `show` 一次取回阶段、修订、指纹、租约和已有检查凭据，不必重读全部历史。区分完整建设、参考建设、已有设计、局部修改、Bug、检查并修复、只梳理、只设计、只检查与发布。明确只梳理/只设计/只检查时分别调用 `site-brief`、`site-design`、`site-check` Skill，返回其回执后停止本流程。
2. **取得首版方案。** 新建、整体改版、主流程变化或高影响需求不清时调用 `site-brief`。只有核心用户、场景、任务、可观察结果、范围和高风险未知已交代，且方案明确确认或获得适用委托，才继续；否则停在方案门禁。局部修改和可直接复现的 Bug 可跳过。
3. **取得可见方向。** 新建、整体改版、主流程/信息结构变化或用户要求“先看看”时调用 `site-design`。**结构选择和风格选择是两道确认**：本轮让用户比较过多个结构时，先由 `site-brief` 用 `confirm-structure` 记录用户选择结构那句原话，再由 `site-design` 在同一结构上给出 2～3 个风格方案，用 `confirm-visual` 记录风格那句。只记录了结构就必须回到第二步，`visual_confirmed` 仍为 false；需要视觉确认的分支必须等体验稿实际展示、模拟范围说明和用户明确确认后继续（能定位会话记录时附 `--anchor` 升级标注）；尚无项目目录时保留原话并在步骤 5 初始化后记录。成熟设计和沿用现状的小修改可跳过。
4. **通过开发门禁。** 回放选定方向、核心任务、首版范围和模拟部分。用户说出“按这个做”“开始开发”等明确授权，或已有适用的全权委托后，才由 `site-builder` 判定开发授权；已有状态时由 `site-brief` 用那句授权的原话记录 `development_authorized=true` 与 `stage=ready_to_build`。用户没说授权时必须停下等待，不能把“好看”“可以”或自己的措辞当授权；尚无状态时保留原话并在步骤 5 初始化后记录。高风险或显著范围变化仍须暂停。
5. **准备工程并计划。** 读 [运行](references/runtime.md) 和 [实施](references/implementation.md)。新项目此时选择技术栈；使用 starter 时只允许目标为空或仅含 `.site`，并保留已有 brief/state。初始化创建默认状态或返回运行配置后，立即调用 `site-brief` 通过其状态协议的门禁工具记录本轮已确认方案、（比较过多个结构时）结构选择、视觉风格、开发授权和 runtime，再创建必要的 `.site/implementation-plan.md`。把首版拆成少量可独立体验的纵向切片；体验稿明确演进或重写。简单修改无需创建计划或状态文件。
6. **连续实现。** 有协作状态时先 `claim` 取 writer 租约并 `start-build`（工具会拒绝门禁缺项和并发写者），再按需读 [组件](references/components.md)。从核心任务的最短完整路径开始，一次完成一个切片；业务规则、状态转换、持久化和 Bug 按风险建立行为检查。项目内依赖、构建错误和普通样式问题自主解决。状态写入一律走门禁工具，不直接编辑 `.site/state.json`。
7. **交接并独立验证。** 开发完成并通过快速自检后，先向用户说明“实现已完成，接下来进行验证”，说明本轮检查范围；验证较久时只在进入新检查轴、发现阻断问题、开始修复或复验时报告阶段变化，不逐条转发工具调用。随后停止自有的体验稿/开发服务，登记仍属本轮的正式服务（owner/PID/端口/根目录），执行 `handoff`：工具会校验 PID 已结束、端口已释放；登记服务必须有存活 PID、监听端口和项目内根目录，但 PID 与端口的对应关系仍由调用者声明。交接会冻结包含 `.site/design` 的源码指纹。随后 `start-verify`（源码若在交接后变化会直接拒绝），再调用 `site-check`，根据改动影响选择 `smoke`、`targeted` 或 `full` 检查档位并写明原因；`full` 必须覆盖五个最低阻断轴，所有档位都不能省略受影响核心任务。所有验证任务或独立检查 Agent 都结束并汇总后，才能生成最终矩阵；不得一边后台验证一边交付。有 failed 项时先向用户说明发现和修复范围，再用 `reopen --check <failed_check_id>` 取回 writer 租约，修完重新 `handoff` 与 `start-verify`；没有失败矩阵时不得抢走 Checker 租约。旧 `check_id` 随指纹变化自动失效，连续两轮没有新证据或进展时用 `block` 记录恢复条件。宿主不能分派 Skill 时执行隔离的检查阶段并说明限制。
8. **通俗交付。** 以 `site-check` 的矩阵凭据为准：只有矩阵指纹与当前源码一致、所有本轮适用且阻断交付的项目均为 `passed`，`deliver --check <check_id>` 才会成功；任一阻断项为 `failed`、`not_run` 或源码已变化时保持 `verifying` / `blocked`。调用 `deliver` 前，先用 `state.py show` 取得 `consent_replay`，把方案确认、（做过结构比较时的）页面结构确认、视觉风格确认和开发授权的原话逐条念回给用户，等用户确认或纠正；用户否认任何一条就先 `reopen`，不得带着错同意交付。确认后再调用 `deliver`，随后说明入口、再次启动、完成范围、体验顺序、实际检查、检查档位、未检查项、数据位置与限制。发布再读 [分发](references/publish.md)，其中公开部署属于不可逆动作。

## 快速分支

- 局部文案、颜色、间距：直接修改正式源码，再执行相称检查；不为此创建 `.site`。
- Bug：先复现用户症状，再修复并覆盖原症状，不机械重走发现和视觉流程。
- 已有设计：读取并沿用；只有整体方向或结构存在未决项才调用 `site-design`。
- 大型愿景：调用 `site-brief` 保留完整愿景并切出本轮目的地，不一次承诺完整平台。

## 协作回执

最终返回：项目入口、完成的首版能力、各 Skill 交接结果、矩阵凭据 `check_id` 摘要、数据位置、限制和下一步。`site-builder` 是开发授权和交付判断的唯一负责人，`site-brief` 的门禁工具是协作状态的唯一写入者；不得根据草案文件、视觉称赞或构建成功推断确认或交付。
