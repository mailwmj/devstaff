# 渐进式建站

## 协作契约

交接或恢复会话时读 [上下文契约](../site-brief/references/context-contract.md)。术语与确认模型以 [领域术语](../CONTEXT.md) 为准；状态、交接、交付和原话规则以 [状态协议](../site-brief/references/state.md) 为准；检查证据以 [验证规则](../site-check/references/verification.md) 为准。

| 字段 | 本 Skill 的接口 |
| --- | --- |
| `reads` | 最新请求、活跃源码、brief、适用的页面设计合同、实施计划与 `state.py show` |
| `writes` | 正式源码与必要的实施计划；状态请求交给 `site-brief` 的门禁工具 |
| `schema` | `needs_user / blocked / delivered`；附入口、切片、变更与验证限制 |
| `handoff` | 按状态协议把 Writer 交给 `site-check`；失败矩阵只用于受控修复回流 |
| `evidence` | 实际入口、核心任务结果、检查矩阵和未验证限制 |

## 执行

1. **识别请求和工程。** 读取源码、原生说明、已有 `.site` 记录和状态；区分完整建设、参考建设、已有设计、局部修改、Bug、检查并修复、只梳理、只设计与只检查。明确只梳理/只设计/只检查时转交对应 Skill 并停止。
2. **取得首版方案。** 新建、整体改版、主流程变化或高影响需求不清时调用 `site-brief`；方案未确认前不制作正式设计或源码。局部修改和可直接复现的 Bug 可走快速分支。
3. **取得可见方向。** 新建、整体改版、主流程/信息结构变化或用户要求“先看看”时调用 `site-design`。结构比较、风格确认和页面设计合同按 `site-design` 与状态协议执行，不在本 Skill 重建规则。
4. **准备工程。** 读 [运行](references/runtime.md) 和 [实施](references/implementation.md)，选择技术栈、创建必要的实施计划，并确保设计合同覆盖本轮页面、状态和验收目标。简单修改无需创建计划或状态文件。
5. **连续实现。** 有状态时按状态协议领取 Writer 租约并开始构建；以页面设计合同为视觉事实来源，按可独立体验的纵向切片完成核心路径。状态文件不直接编辑。
6. **交接与验证。** 停止本轮体验稿/开发服务后，按状态协议完成交接和冻结，再调用 `site-check` 按改动影响选择 `smoke`、`targeted` 或 `full`。检查档位、浏览器能力、证据、修复回流和 `check_id` 规则全部以 [验证规则](../site-check/references/verification.md) 为准。
7. **修复与复验。** 只根据当前失败矩阵修复，重新交接和验证；没有新证据或进展时按状态协议停止并记录阻塞。
8. **交付。** 仅在当前源码指纹、检查矩阵和确认记录都满足状态协议时交付；交付前按协议回放原话，随后用通俗语言说明入口、范围、检查结果、限制和数据位置。

## 快速分支

- 局部文案、颜色、间距：直接修改正式源码并执行相称检查，不创建 `.site`。
- Bug：先复现症状，再修复并覆盖原症状，不机械重走发现和视觉流程。
- 已有设计：读取并沿用；只有整体方向或结构存在未决项才调用 `site-design`。
- 大型愿景：调用 `site-brief` 保留完整愿景并切出本轮目的地。

## 协作回执

返回项目入口、完成的首版能力、各 Skill 交接结果、检查摘要、数据位置、限制和下一步。`site-builder` 是开发授权和交付判断的唯一负责人；状态写入由 `site-brief` 的门禁工具负责。
