# 首版梳理与协作记录

## 协作契约

交接或恢复会话时读 [上下文契约](references/context-contract.md)，按统一回执 schema 返回，不另建上下文副本。

| 字段 | 本 Skill 的接口 |
| --- | --- |
| `reads` | 最新请求、项目事实、`.site/brief.md`、`state.py show`；缺少材料只补阻塞首版的未知 |
| `writes` | `.site/brief.md`；门禁状态与派生恢复快照仅由 `state.py` 写入 |
| `schema` | `ready / needs_user / blocked`；内容区分事实、决定、假设、首版切片、包含、排除与风险 |
| `handoff` | `ready` 返回调用者或建议下一 Skill，不代表视觉确认、开发授权；未决项停在对应决定 |
| `evidence` | 可定位的项目事实、查证来源和用户原话记录；无法查证的内容保留为假设 |

把模糊愿景收敛为创作者能确认、其他 site Skill 能消费的 brief，并集中维护跨 Skill 状态。用户不需要理解阶段、技术栈或 Skill 名称。

## 选择分支

- **梳理首版：** 执行步骤 1～7。
- **记录协作结果：** 其他 site Skill 已完成其职责内判断时，直接执行步骤 6；不重开需求访谈，也不替调用者改变结论。

## 执行

1. **恢复上下文。** 先读用户材料、现有 `.site/brief.md`、`.site/state.json` 和相关工程事实。将内容区分为事实、决定、假设、待确认；旧记录与用户最新表达冲突时保留差异。由其他 Skill 调用时只补阻塞首版的未知。
2. **找到当前前沿。** 读 [需求发现](references/discovery.md)，只询问会改变核心任务、体验边界或风险，前置条件已清楚且相互独立的问题，一轮问完再等回答。给出通俗选项、影响和推荐项；答案依赖本轮未决问题的排到下一轮。
3. **检验理解。** 对业务词冲突先对齐含义并当场写入 brief 的“业务词义”，再用具体场景回放“谁在什么情况下做什么、看到什么结果”，必要时补一个边界场景逼出边界。已有工程时与代码实际行为核对；词义或行为冲突都当面指出，既不静默替用户决定，也不静默采信一边。
4. **按需查证。** 外部事实会改变首版时读 [轻量研究](references/research.md)。事实由 Agent 查，产品取舍仍由创作者决定。需要外部事实的前沿问题不阻塞提问：派独立调查去查，只把依赖该事实的问题留到下一轮，其余前沿照常问；宿主不支持独立调查时在同一会话内查询，并说明这一限制。
5. **收敛首版。** 保留完整愿景，从中推荐一条可完整体验的核心任务；明确可观察结果、包含、暂不包含、风险和剩余假设。大型愿景只确定本轮目的地和当前前沿，不展开路线图。
6. **增量记录。** 读 [brief 规则](references/brief.md) 与 [状态协议](references/state.md)。复杂、跨会话或需要交接时更新 `.site/brief.md`；状态一律通过 `references/state.md` 中的门禁工具写入，不直接用编辑工具改 `.site/state.json`。记录确认时用 `--quote` 原样抄录用户那句原话，保留换行和空格；能定位到宿主会话记录时再加 `--anchor` 升级标注，读不到或读不懂都不阻塞。确认归属由**当时正在询问的决定、Agent 已说明的下一步后果和用户紧接着的答复**共同决定，不按孤立词面判断，也不把较晚答复倒填给较早门禁；早期记录缺失时只能使用当时真正回答该决定的原话，不存在就重新询问。**页面结构的选择和视觉风格的选择是两条记录**：记录方案确认时用 `--structure-directions N` 说明本轮让用户比较几个结构——只给一个结构要显式写 1，不写就按多结构兜底；多结构轮次先用 `confirm-structure` 记录结构那句，再用 `confirm-visual` 记录风格那句；两者的 `--prototype` 都必须是项目内普通文件，不得使用目录或符号链接。只拿到结构选择时如实写成"结构已确认、风格待选"，不得当作视觉确认。**不得把用户的措辞改写成自己的话，也不得由于工具无法核验就替用户编造同意**——工具记录的是声明，验证同意只能由用户本人在交付回放时完成。调用者给出判断和所需字段，工具负责校验、原子替换、递增修订和追加紧凑跃迁历史。上游决定变化时执行下游失效规则，不留下新方案配旧视觉、新结构配旧风格或旧授权。
7. **确认并交接。** 回放完整愿景、核心用户与场景、首版核心任务、可观察结果、范围、假设和风险，并明确当前只在确认首版方案。只有用户对这项回放明确认可，或低风险范围获得明确委托，才确认方案；用户还没有作出这项决定时继续澄清，不要拿后续结构、视觉或开发阶段的笼统肯定补记方案，也不要用模型措辞替代。输出协作回执后停止。

## 协作回执

返回：项目、`ready | needs_user | blocked`、本轮新增/变化的事实与决定、被更新的记录、仍未确认的高风险项、建议下一 Skill。`ready` 只表示首版方案已确认，不表示视觉确认或开发授权。

不得创建体验稿、实施计划、依赖或业务代码；不强制 issue、ticket 和额外路线图，也不为取舍另建 ADR 文件——难逆转且有理由的取舍写进 brief 的“已确认决定”。
