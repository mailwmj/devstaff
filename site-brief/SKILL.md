# 首版梳理与协作记录

把模糊愿景收敛为创作者能确认、其他 site Skill 能消费的 brief，并集中维护跨 Skill 状态。用户不需要理解阶段、技术栈或 Skill 名称。

## 选择分支

- **梳理首版：** 执行步骤 1～7。
- **记录协作结果：** 其他 site Skill 已完成其职责内判断时，直接执行步骤 6；不重开需求访谈，也不替调用者改变结论。

## 执行

1. **恢复上下文。** 先读用户材料、现有 `.site/brief.md`、`.site/state.json` 和相关工程事实。将内容区分为事实、决定、假设、待确认；旧记录与用户最新表达冲突时保留差异。由其他 Skill 调用时只补阻塞首版的未知。
2. **找到当前前沿。** 读 [需求发现](references/discovery.md)，只询问会改变核心任务、体验边界或风险，且前置条件已经清楚的问题。给出通俗选项、影响和推荐项。
3. **检验理解。** 对业务词冲突先对齐含义，再用具体场景回放“谁在什么情况下做什么、看到什么结果”；发现冲突时不静默替用户决定。
4. **按需查证。** 外部事实会改变首版时读 [轻量研究](references/research.md)。事实由 Agent 查，产品取舍仍由创作者决定。
5. **收敛首版。** 保留完整愿景，从中推荐一条可完整体验的核心任务；明确可观察结果、包含、暂不包含、风险和剩余假设。大型愿景只确定本轮目的地和当前前沿，不展开路线图。
6. **增量记录。** 读 [brief 规则](references/brief.md) 与 [状态协议](references/state.md)。复杂、跨会话或需要交接时更新 `.site/brief.md`；按调用者判断和用户依据原子更新状态。上游决定变化时执行下游失效规则，不留下新方案配旧视觉或旧授权。
7. **确认并交接。** 回放完整愿景、核心用户与场景、首版核心任务、可观察结果、范围、假设和风险。只有用户明确认可，或低风险范围获得明确委托，才确认方案；输出协作回执后停止。

## 协作回执

返回：项目、`ready | needs_user | blocked`、本轮新增/变化的事实与决定、被更新的记录、仍未确认的高风险项、建议下一 Skill。`ready` 只表示首版方案已确认，不表示视觉确认或开发授权。

不得创建体验稿、实施计划、依赖或业务代码；不强制 ADR、issue、ticket 和额外路线图。
