# 首版梳理与协作记录

把模糊愿景收敛为创作者能确认、其他 site Skill 能直接消费的首版，并集中维护协作状态。用户不需要理解阶段或技术栈。

## 路由

- 用户只要需求梳理：完成首版发现与确认。
- 其他 Skill 已给出职责内结论：只增量记录结果，不重开访谈，不替调用者改变结论。

## 执行

1. **恢复事实。** 读取用户材料、现有工程、`.site/brief.md` 和 `state.json`。处理多轮密集输入与多模态票据：当用户连续发送补充信息或机票、酒店、火车票等多模态票据图片时，提取行程、人员、航班、住宿等事实沉淀至 brief 事实层，避免在连续输入下丢失上下文或遗漏关键事实。区分事实、决定、假设和待确认；新表达与旧记录冲突时保留差异。
2. **找到当前前沿。** 只问会改变核心任务、体验边界或高风险的未知。读 [需求发现](references/discovery.md)，一轮询问彼此独立的问题，使用通俗选项、影响和推荐；能从项目查到的事实不问用户。
3. **校验词义和场景。** 业务词冲突先对齐含义，再回放“谁在什么情况下做什么、看到什么结果”，必要时加一个边界场景。已有工程时与实际行为核对。
4. **收敛首版。** 保留完整愿景，推荐一条可完整体验的核心任务；明确成功、失败恢复、中途退出、再次打开、设备、本地化、包含、排除、风险和剩余假设。大型愿景不一次承诺完整平台。
5. **增量记录。** 复杂、跨会话、收到多轮输入补充或多模态票据解析后，按 [brief 规则](references/brief.md) 增量更新 `.site/brief.md`，将提取的事实字段沉淀至事实层。状态只按 [状态协议](references/state.md) 通过 `scripts/state.py` 写入；`--quote` 原样保存用户表达。旧决定变化时使不再适用的下游确认、授权和检查失效。
6. **确认并交接。** 用普通话回放最终用户、场景、首版任务、可见结果、范围、假设和风险。只有用户认可或低风险范围获得明确委托时才确认方案。

## 回执

返回项目、`ready | needs_user | blocked`、本轮新增/变化的事实与决定、更新的记录、高风险未知和下一 Skill。`ready` 只表示首版方案成立，不表示结构、视觉或开发已确认。

不得制作体验稿、实施计划或业务代码；不得把行业惯例、规范或模板写成用户需求。
