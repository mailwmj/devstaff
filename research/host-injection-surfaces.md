# 宿主注入面与 bootstrap 方案（host-agnostic）

> 目标：让用户侧 `templates/AGENTS.md` 的路由表在**每个会话开始时自动进入模型上下文**，不需要用户每次手动选择。
> 约束（由项目方确定）：**不用 hook**；**不绑定 DSH**——用户的 agent 不是 DSH。
> 关联：[`superpowers-handoff-comparison.md`](superpowers-handoff-comparison.md)（B 侧四层机制与逐条对照）

## 1. 为什么要单独讨论注入

第 1 层（路由边）和门禁都已具备；缺的是**动态触发**：模型凭什么会在该用 `site-brief` 的时候去用它。四个 Skill 的 `description` 只提供"被发现"的机会，不提供"被遵守"的保证——小白说"帮我做个网站"，模型完全可以读成"我自己开干"。

superpowers 的结论可以直接借用：

> **The bootstrap is the entire integration.** 没有它，skill 文件是惰性的——在磁盘上存在，但永远不会被调用。

因此本项目的关键不是再写规则，而是**把一个载体可靠地送进上下文**。

## 2. 不用 hook 的直接后果

排除 hook 后，只剩两种载体形态：

| 形态 | 载体 | 首请求必达 | 依赖 |
| --- | --- | --- | --- |
| **B：进程内插件/扩展** | 宿主 API 注册 + 生命周期回调注入 | ✅ | 需要该宿主有插件体系，且我们要为它各写一份 |
| **C：指令文件** | 宿主启动时自动加载的 `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` 等 | ✅ | 宿主的指令文件约定 |

**本项目应选 C 为主、B 为辅**，理由：

1. **C 是所有主流宿主的最小公约数**——`AGENTS.md` 已被 Claude Code、Codex、Gemini CLI、Cursor 等共同接受，且本项目 `install.py` 的安装目标本来就是宿主的 skills 目录；
2. **不需要为每个宿主写代码**。B 的代价是 N 份插件实现 + N 份维护，而本项目要交付给"没有编程背景的中文用户"，装机路径越短越好；
3. **没有 hook 的脆弱性**。hook 是宿主外部进程，存在超时、detached 运行、错过首个请求、格式差异等问题（已在其他宿主上被反向证实）；指令文件是宿主自己加载的，没有这层不确定性；
4. **`templates/AGENTS.md` 已经写好**，11,297 字节，本就是按指令文件形态设计的（第一节到第八节都是给 agent 读的指令）。它是现成的 C 载体，不需要改造。

**B 只在宿主明确支持且愿意维护时才做**，且必须遵守 superpowers 那条铁律：**安装物自己携带，绝不编辑用户的全局配置**。

## 3. 宿主必须满足的一个硬条件

无论 C 还是 B，判据只有一条（照搬 superpowers 的"定义完成"）：

> 宿主必须能在**每个会话开始时、无需用户按会话手动 opt-in** 地把我们的文本送进模型上下文。

**不满足这条的宿主，就是不能支持**——典型反例：只能靠用户每次粘贴一段提示词、或每次手动启用某个模式。这类"集成"在小白的真实使用里等于不存在。

C 形态下，还要区分两种加载语义，**必须实测、不能假设**：

| 语义 | 表现 | 是否可用 |
| --- | --- | --- |
| **真内联** | 文本**无需工具调用**就已在上下文里 | ✅ 可用 |
| **@-include 提示** | 宿主把 `@./path` 当成"模型可能去读"的提示，产生一次文件读取工具调用 | ⚠️ 不算可靠注入，需改为内联 |

验证手段是**唯一标记测试**（unique-marker test）：往载体里放一个无意义 token，开干净会话，确认该 token **在没有工具调用的情况下**已进入上下文。这个测试比通读配置可靠得多。

## 4. 载体与内容的关系：单一事实来源

**只有一份路由正文：`templates/AGENTS.md`。** 它同时是：

- **C 的载体内容**——复制为用户项目的 `AGENTS.md`，或宿主全局指令文件；
- **B 的内容来源**——宿主插件读取它并注入。

这样避免"插件里一份、项目里一份"的双份维护漂移，也就是本项目在 `skills.json` / `SKILL.md` / `tests/scenarios.md` 之间已经踩过的那类坑。

体积：11,297 字节。已核对正文**不含 `{{`**——这条对某些宿主很重要（它们的提示词/指令模板会在渲染期严格解析 `{{…}}`，出现未注册的组会渲染失败）。**今后任何编辑都必须保持这个约束**，建议由校验脚本断言。

## 5. 需要为宿主记录的适配信息

**目标宿主已定为 Claude Code + Codex**，逐条清单见 [`templates/hosts/README.md`](../templates/hosts/README.md)。本节保留通用要求。

每个受支持宿主一份适配记录（不是代码，是一份清单），四块：

1. **载体位置与文件名**：C 形态下该宿主读哪个文件、放在哪、支持哪些候选名、是否支持嵌套/overlay；
2. **加载语义**：真内联还是 @-include 提示（必须附唯一标记测试结果）；
3. **能力档位**（决定 `templates/AGENTS.md` 第六节各条落哪一档）：

   | 能力项 | 有 | 无 |
   | --- | --- | --- |
   | 调用其他 Skill | 正常路由 | 同会话内按协作顺序执行，说明未隔离 |
   | 派独立 Agent | Writer/Checker 真隔离 | 同会话执行隔离阶段，说明限制 |
   | 浏览器实测 | 视觉/交互/再次打开可实测 | 一律标 `not_run` |
   | 读会话记录（`--anchor`） | 标注可升 `quote-matched` | 降级 `agent-reported`，不阻塞 |

4. **降级话术**：缺能力时如实标注的确切措辞，**必须与 `templates/AGENTS.md` 第六节一一对应**（那节是策略，这份是执行）。

**建议**：把这份清单做成表格放进 `templates/hosts/README.md`，一行一个宿主。**在确定目标宿主之前不要为任何单个宿主写安装细节**——那是会在宿主变更时立刻作废的投入。

## 6. `--anchor` 的能力边界（已核实）

`site-brief/scripts/state.py` 的 `anchor_text` / `anchor_user_messages` 是**刻意 host-agnostic** 的：

| 维度 | 支持 |
| --- | --- |
| 编码 | 明文、gzip（`1f 8b`）、zstd（`28 b5 2f fd`，走 `import zstandard`） |
| 结构 | JSON 数组或 JSONL，逐行容错（坏行跳过不报错） |
| 消息形状 | 顶层 `role`/`content`，或嵌套在 `message` 下 |
| 正文 | `content` 为字符串，或 `[{type:'text', text:…}]` 块数组 |
| 角色 | 用户 = `user`/`human`；agent = `assistant`/`agent`/`model`/`system`/`tool` |

**读不到是正常结果而非错误**：`--anchor` 缺失或不可读都只降级为 `agent-reported`，**流程继续、不阻塞**。这正是项目"门禁不得依赖宿主内部实现"的体现，也因此不需要为任何宿主预先适配。

**一个可移植性缺口**：`anchor_text` 只尝试 `import zstandard`，而 Python 3.14 起标准库已有 `compression.zstd`。本机实测：`zstandard` **不可导入**、`compression.zstd` **可用**。因此遇到 zstd 会话记录时，它会在"解释器其实解得开"的情况下**静默降级为读不到**。修法很小——按 `zstandard` → `compression.zstd` 顺序回退即可。

> 这条与宿主无关，纯属本机 Python 依赖；但它会让"能升级的标注"平白降级，值得单独修。

## 7. 验收：三层，全绿才算通过

用小白口吻的一句话验收，不靠通读配置：

> **干净会话发「帮我做个网站」。**

| 层 | 判据 | 不通过的常见原因 |
| --- | --- | --- |
| **L1 注入** | 问会话"你的路由规则里'验收'分几种情况"，能答出按运行态分两种 | 载体没被加载（位置/文件名不对，或只是 @-include 提示） |
| **L2 技能可见** | 会话 skill 目录里出现四个 `site-*` | 安装路径不在被扫描根下；目录 bundle 层级不对（多数宿主只认 `<dir>/<name>/SKILL.md`，不认嵌套 `**/SKILL.md`） |
| **L3 行为** | 在写任何代码前进入 `site-brief`，并停在方案门禁 | 路由存在但优先级不够或没被读进去 |

L3 的三个可判定信号：① 未创建正式源码；② 出现方案/范围/核心任务的回放与提问；③ 未越过方案门禁去 `site-design` 或初始化工程。

**L1/L2 通过而 L3 失败最值得盯**——内容在了但没被遵守，属"模型合理化"，靠 `templates/AGENTS.md` 第五节那张反合理化表压制。

## 附：方法留档

**已排除：hook 形态（Shape A）。** 除项目方明确不用之外，它本身也是三者中最脆的：依托宿主外部进程，存在超时、脱离运行、错过首个请求、只支持部分输出字段等问题。不用它是**主动的稳健性选择**，不是能力缺失。

**候选宿主调查（不构成目标）。** 曾对本机 DSH Desktop 做过完整反向取证（asar 解包逐包核对），确认它同时提供指令文件链与 `SessionStart` hook，且会话日志为 zstd+JSONL 明文可读。**但用户的 agent 不是 DSH，因此该调查不作为交付依据**，仅留记录避免重复劳动。

**反向取证的可复用方法**（换成目标宿主时照用）：

1. 查宿主的插件/扩展/hook/skill/context-file 文档；
2. 找一个真实的第三方扩展当范例——能跑的例子胜过文档；
3. 逆向：`strings` 二进制或解包安装树，找事件名、配置路径、指令文件名；
4. **问正在运行的模型**"列出你能调用的全部工具的确切机器名"——避免臆造工具名；
5. **唯一标记测试**证明假设，绝不用"父宿主的做法应该能迁移"来推断派生宿主。

**未能验证**：未在 Claude Code / Codex 上实际跑通第 7 节三层验收（只做了官方文档与格式核对）；未实测两家同时生效时的重复 token 量。
