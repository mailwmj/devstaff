# 同意门禁机制评审：从"硬编码是否限制模型"到"这套机制是否成立"

> 日期：2026-09-11
> 对象：`site-builder` / `site-brief` / `site-design` / `site-check` 组成的建站 Skills（`skills.json` 版本 0.7.0）
> 方法：通读四个 SKILL.md、全部 references、五个脚本（`state.py`、`check.py`、`site.py`、`design.py`、`preview.py`）、评测方案与 2026-09-11 端到端报告；在当前宿主（DSH，macOS）实测门禁工具的输入链路；运行 `tests/gate_flow.py` 与 `scripts/verify_skills.py`
> 性质：评审结论，尚未实施。文中的"建议"均未改动代码

---

## 0. 结论摘要

最初的问题是"硬编码太多，会不会限制模型发挥"。经过三轮推导，结论发生了实质变化：

1. **该硬的地方还不够硬，不该硬的地方硬过头了。** 真正需要机械保证的（交付物等于被批准物、证据未被改写）已实现得不错；而最可逆的决定（方案确认、视觉选择）反而用了最重的密码学锚定。
2. **你的担心只对了一半。** 限制强模型的不是门禁，而是固定数字（3～5 问、2～3 方向）、配方菜单（10 个 recipe）、技术脚手架（`web/` + Python 预览服务器）。门禁本身在*应当*硬的范畴内。
3. **但更根本的问题在第三轮暴露：这套同意门禁在原理上不可能成立。** 它试图用"Agent 可写的文件"去证明"Agent 没越权"。这是范畴错误，不是实现缺陷。
4. **因此"补丁打不完"不是终点，方向本身是错的。** 正确做法不是适配更多宿主，而是反转依赖：把宿主适配从*运行前提*降为*可选增强*，把人的判断从*机器验证*降为*诚实声明 + 交付时交还本人*，并把全部机械强度集中到一条真正可证的不变量上。
5. **当前项目已经为这套机制付出了可测量的代价**，且其中三项失败是**架构自己制造**的，不是用户需求不清造成的。

**一句话：** 不要试图在 Agent 自己的环境里证明 Agent 守规矩。删到只剩"交付物 == 被批准物"这条不变量，其余还给人和宿主。

## 1. 第一轮：按立意评估硬编码

### 1.1 评判标准来自项目自己的定位

`REQUIREMENTS.md` §1 明确：核心价值不是更快产生代码，而是①帮用户说清第一版要解决的问题；②正式开发前用低成本可见成果确认方向；③Agent 包办依赖、运行、构建、验证；④把大愿景收敛为可验证小版本。目标用户是"没有编程背景的中文用户"（`tests/novice-user-evaluation.md` 的林晓雨画像）。

因此成功标准是：问题少而准、可见方向真实不造假、成果能再次打开、高风险不越权、不把技术决策推给用户。

### 1.2 硬编码分层

| 层 | 具体内容 | 位置 | 该不该硬 |
| --- | --- | --- | --- |
| **L1 不变量** | transcript 锚定同意、源码指纹冻结、矩阵证据哈希、Writer/Checker 租约、PID/端口登记 | `site-brief/scripts/state.py`、`site-check/scripts/check.py` | **该硬**（但其中"transcript 锚定"后来被证明不成立，见 §3） |
| **L2 流程编排** | 9 个阶段、固定 12 条命令、`handoff → start-verify → deliver` 全串行、纵向切片模板 | `site-brief/references/state.md`、各 SKILL.md | 半该硬：阶段与"证据不足即拒绝跃迁"该硬；对单页小站也走满全套属过重 |
| **L3 内容与设计判断** | 每轮 3～5 问、2～3 个方向、默认只做一个核心页、"AI 味"清单、10 配方 / 10 配色菜单 | `site-brief/references/discovery.md`、`site-design/references/*`、`site-design/assets/design/tokens.json` | **大多不该硬** |
| **L4 技术脚手架** | `web/` 目录约定、`preview.py`、`启动.command/.cmd`、static/tool 模板 | `site-builder/scripts/site.py`、`site-builder/assets/templates/` | 对小白有用，但把技术默认前移到了理解项目之前 |

### 1.3 第一轮的三个判断

- **不成立的担心：** 门禁机械化不限制模型发挥。项目自己的报告证明，只靠 SKILL.md 文字规则时模型确实越门（`tests/runs/novice-e2e-20260911/report.md` 否决项 1、7）。
- **成立的担心之一：** 配方菜单与"反默认"目标自相矛盾。`design-quality.md` 用大量篇幅要求"反默认 / 替换检查 / 项目标志"，而 `tokens.json` 递上 10 个现成 recipe。文档反复声明"recipe 不是方向"，**但菜单本身就是一个强先验**——它把"推导方向"退化为"挑配方"，恰好产出它想避免的模板感。
- **成立的担心之二：** 固定数字把"按不确定性决定"变成"凑数"。文档都加了 hedge（"未知很少时可以少问"），但数字比原则更容易被遵循。
- **成立的担心之三：** starter 把技术默认前移。`site.py init` 只给 `web/` + Python `http.server` 一种形状，与 `runtime.md`"技术栈服从已确认范围"的声明存在张力。

### 1.4 第一轮提出的 P0（后来被推翻）

当时提出两条 P0：①`state.py` 增加 zstd / 逐宿主适配；②加强 provenance 校验。

**这两条在第二轮被重新定性**：它们不是"还没做的补丁"，而是一个错误方向上的继续投入。

## 2. 第一轮实测：P0 的具体证据

轮询宿主环境得到的可复现事实：

| 项 | 实测结果 |
| --- | --- |
| 宿主会话记录形态 | `$DSH_HOME/sessions/<project>/<id>/session.v3.jsonl.zstd` |
| `state.py` 接受的后缀 | `SESSION_SUFFIXES = ('.jsonl', '.json', '.ndjson')` —— `.zstd` 被直接拒绝 |
| 本机 zstd 能力 | 无 `zstd` 二进制；无 `python zstandard` 模块；Python 3.9.6（无 `compression.zstd`）；无 node |
| 结论 | `confirm-concept` / `confirm-visual` / `authorize-build` **无法用真实记录执行**；按 `state.md` 规定只能标"未验证"，即三道门禁全部失效 |

同时发现**抗伪造能力被 README 高估**：

- `locate_session()` 接受任意路径的 `.jsonl`，不校验来源。Agent 可以自己写一个 `role: user` 的 jsonl 再指过去。
- "一句话不能过两道门禁"只比较 `transcript + message_id`（`record_consent()`），**把文件复制到另一个路径即可绕过**。
- 因此 `README.md` 第 35 行"Agent 不能自己写一句『用户同意了』"是**过度承诺**。

**过度承诺比诚实的能力边界更危险**——它让审查者跳过人工核对。

## 3. 第二轮：为什么"继续打补丁"是错的

### 3.1 反转问题：门禁到底想保证什么

要保证的性质是：**Agent 不得越过用户尚未做出的决定。**

能强制它的只有两个来源：

1. **人** —— 只有人知道自己有没有同意；
2. **宿主 / 平台** —— 审批通道、权限边界，由别人维护，Agent 无法伪造。

**项目内的一切文件都做不到，因为 Agent 能写文件。** 这不是"当前没做好"，是范畴错误。

### 3.2 现有 transcript 方案同时违反了自己依赖的两个前提

- **不 host-portable：** 它依赖宿主内部实现（格式、压缩、路径），而这些不可预知。每支持一个宿主就要打一个补丁，永远打不完。
- **不 forge-proof：** 它挑的是文件，而 Agent 能写文件。

所以它既没有可移植性，也没有它宣称的抗伪造性。

### 3.3 正确的切法：按"谁能验证"重切状态机

现在的 `state.py` 把两类完全不同的东西混在同一套"证据"话术里。拆开就清楚了：

| 类别 | 内容 | 谁能验证 | 处置 |
| --- | --- | --- | --- |
| **A 类：项目内自指事实** | 指纹、交接冻结、证据 sha256、矩阵阻断项、租约、PID 存活、端口占用 | **本地脚本，且与宿主无关** | 保持机械；这是价值大头，且天然跨平台 |
| **B 类：人的判断** | 方案确认、视觉确认、开发授权 | **只有人** | 本地脚本**永远无法验证**，不要假装能 |

现状是：A 类做得很好（约 700 行，纯本地、纯标准库、零宿主知识），却把 B 类也塞进同一套话术，于是 B 类既拿不到真证据，又把 A 类的可移植性一起拖下水。

### 3.4 关键架构动作：把宿主知识从"前提"改成"可选增强"

这是回答"不然就一直打补丁"的那一步——**反转依赖方向**：

```text
现在的依赖：
  同意门禁 → 必须读到宿主 transcript → 未知宿主 = 产品停摆
              ↑ 每支持一个宿主打一个补丁（永远打不完）

应该的依赖：
  同意记录 = 声明（永远可用，零宿主知识）
              ↑ 可选增强：能读到宿主记录时，升级为"已锚定"
```

一旦这样切：

- **不补丁也不影响可用性** —— 产品在所有宿主上都能走完；
- **补丁变成单调增强** —— 加宿主适配是"让记录更强"，不是"让产品能跑"；
- **未知环境优雅降级**，而不是三道门禁全死、用户不知道发生了什么。

### 3.5 把真正的保证放到有保证的地方

既然同意不可机械证明，就把硬度推到**确实可证明、且对用户最有价值**的地方。那正是 `deliver`：

> **交付的东西 === 你批准的那个东西**（同源码指纹、证据未被改写、阻断项全过）

这是纯哈希、A 类、零宿主知识、跨平台永远成立。`fingerprint` / `handoff` / `deliver` 已经是全仓最扎实的部分，应该**加码**，而不是把精力花在同意门禁上。

B 类改为"**可见 + 可审计 + 交付时暴露给人**"：

- 记录里明写 `basis: agent-reported`，不再冒充 `verified`；
- append-only，带逐字引语、时间、actor，事后任何人可比对真实对话；
- **交付时向用户回放三条同意的原文引语**，让错的同意在最便宜的时刻被本人抓到；
- **高风险不可逆事项**（装系统、付费、第三方授权、敏感数据）不自己重造机制，直接走宿主已有审批通道——那是真正非伪造、且由别人维护的通道。

### 3.6 那 2026-09-11 的两个否决项怎么办

诚实回答：**那类失败本来就防不住。**

那次不是恶意伪造，是"匆忙的 Agent 在回放前就写了 `concept_confirmed=true`"。任意可写的本地文件都挡不住它——包括后来的 transcript 方案（它也没挡住；报告显示两条会话都越了门）。

换成声明模型后，靠三件事兜：

1. 门禁命令仍需显式 basis，append-only + revision 自增，**跃迁可见**；
2. 交付时把同意原文推给用户，**由本人纠错**；
3. 真正的产品解不在门禁，而在**首轮回复结构**——第一句话就该问问题。

不要用一个不可能成立的密码学保证，去替代一个本该由流程和呈现解决的问题。

## 4. 第三轮：这套东西为什么必然越长越多

### 4.1 两个早期选择构成闭环

回溯最初的岔路口，只有两个选择：

1. **把"可机械验证的过程合规"当作成功判据** —— 因为成果质量不可机械验证；
2. **把信任锚点放在 Agent 可写的文件系统里** —— 因为进程内没有别的选择。

两个选择各自都合理，合起来就是**无底洞**：每发生一次失败就新增一条规则。

**项目历史就是证据：** `gate_flow.py`（415 行）是在 2026-09-11 报告之后才补的；版本已到 0.7.0；而那次报告的两个否决项，在补之前和补之后都真实发生过。**规则在增长，失败模式没被消灭。**

### 4.2 根本错配：手段与目标

- 用户真正会被伤害的情形是**做出了错的东西**（白做一轮）；
- 机制实际检测的是**没有留下问过的痕迹**（流程违规）。

因为结果无法机械检测，就退而检测过程。这在工程上很常见，问题是一旦代理指标被写进硬门禁，**它就会取代目标本身**。`state.py` 里那套 transcript 定位、哈希、复用拒绝，防的全是"没有留下痕迹"，而不是"做错了东西"——它连一次"用户真的被问过但答非所问"都防不住。

更关键的是：**机制在检测"痕迹"，而 Agent 恰好在"生成痕迹"上是完美的。你能对一句谎话做 sha256。**

## 5. 当前项目里的具体问题（按伤害排序）

### 5.1 并发控制被施加在一个单写者系统上

租约、`--expect-revision`、Writer/Checker 串行、交接冻结、PID/端口登记——解决的是"两个写者同时改一份状态"。

但目标用户的真实场景是：一个 Agent、一个用户、一台机器。**什么时候真有两个写者？只有评测脚本并行回放的时候。** 这套最复杂的机械装置是为**测试台**服务的，不是为林晓雨服务的。

### 5.2 协议自己制造了新的失败模式（最有说服力）

2026-09-11 报告中的"非阻断"项里有三条：

| 现象 | 成因 |
| --- | --- |
| `.site/brief.md` 记 4174，README/state 记 4175 | **多文件状态同步**带来的漂移 |
| 主线 C 生成体验稿后没有可见回复和入口 | **Skill 间交接**丢掉了成果 |
| 全局安装的 `site-brief` 缺失、其余三个哈希不一致 | **四件套强耦合安装**带来的版本问题 |

这三条都不是"用户想法没问清"造成的，**是架构自己产生的**。为了减少错误方向的浪费，引入了一套会产生新浪费的装置。

### 5.3 硬度分配是反的

| 决定 | 可逆性 | 当前强度 |
| --- | --- | --- |
| 方案确认 / 视觉选择 | 完全可逆，改一句话的事 | **硬门禁 + 密码学锚定** |
| 装系统软件 / 付费 / 第三方授权 / 儿童数据 | 不可逆 | **散文规则："通常需要暂停确认"** |

最不可逆的事靠提示词，最容易反悔的事靠代码。**这个倒置本身就是大量复杂度的来源。**

### 5.4 代理指标挤占了稀缺资源

| 项 | 行数 |
| --- | ---: |
| `site-brief/scripts/state.py` | 966 |
| `site-check/scripts/check.py` | 534 |
| 治理类小计 | **1500** |
| `site-builder/references/implementation.md` | 54 |
| `site-builder/references/components.md` | 22 |
| 产品指导类小计 | **76** |

Context window 是唯一的稀缺资源。Agent 把它花在跑 12 条命令上，就没花在想这个页面该长什么样上。

评测权重分布（`tests/novice-user-evaluation.md` §6.1，总分 100）：

- 治理与流程类：门禁授权与风险 15 + 验证与证据纪律 15 + 协作边界与状态一致性 5 = **35**
- 产品与体验类：小白沟通 10 + 需求理解 15 + 体验稿特异性 10 + 视觉完成度 10 + 正式成果 15 + 通俗交付 5 = **65**

治理占 35%，对一个用户价值几乎全在产品体验的工具来说偏高。

### 5.5 它给出了一种它并不拥有的确定性

`delivered` 加一个 `check_id`，读起来像"已验证正确"。但 `check.py` 自己写明（`verification.md` §2）：

> 工具能验证证据文件存在、位于项目内、未被改写、且命令证据确实退出 0，但它**无法验证一张截图是否真的证明了所写结论**。

更实际的是：`matrix_check()` 只检查**调用方传入的 items**。所以那套哈希链保证的是**来源**，不是**正确性**。

2026-09-11 报告否决项 7 显示：独立检查判定 `failed` 时，`.site/state.json` 已是 `stage=delivered`。事后补充的硬化能阻止"**被记录为 failed 的阻断项**"进入交付，但无法阻止"**真实存在却从未被列为阻断项的缺陷**"。这是结构性缺口，不是漏了一条规则。

### 5.6 它与产品自己的 UX 主张打架

`REQUIREMENTS.md` §6.1 明确写了全权委托、"你决定"、"按推荐继续"，§5.2 允许把低影响细节记录为 Agent 假设。也就是说，**低风险场景下"直接决定并前进"本来就是想要的行为**。而门禁在最常见的情况下惩罚它。对一个信息不全、习惯说"你看着办"的用户，这套机制的默认反应是拒绝。

## 6. 于是真正的不变量只剩一条

把所有可逆的、靠人判断的东西从机器里拿出来之后，剩下能硬、也该硬的其实非常少：

> **最后交出去的东西，必须等于你批准的那个东西；你授权的边界，必须可见且诚实。**

这条是纯哈希、零宿主知识、跨平台永远成立。

其余的重新分配：

| 决定类型 | 处置 |
| --- | --- |
| **可逆决定**（方案、视觉、局部取舍） | Agent 决定、标为假设、当场展示、用户纠正。错的代价是**一轮迭代**，不是灾难 |
| **不可逆决定**（系统安装、付费、第三方授权、敏感数据） | 不自己重造机制，走宿主已有审批通道 |
| **"用户说过什么"** | 诚实标成 `agent-reported`，append-only，交付时把原话回放给用户本人核对 |

**唯一能验证同意的人就是那个人。** 把验证放回它该在的地方，成本也最低。

## 7. 最新建议

### 7.1 如果只做三件事

1. **删掉"必须指向 transcript"的硬要求。** `confirm-*` 从"验证"语义改为"记录声明"语义，增加可选的 `--anchor`；没有 anchor 不阻塞，只降低标注的可信等级。
2. **反转宿主依赖。** 宿主适配成为可选增强，不是运行前提。未知宿主必须能走完全流程。
3. **收敛到交付不变量。** `deliver` 保持并加强指纹绑定与证据完整性校验；这是唯一值得投入机械强度的地方。

## 9. 尚未解决 / 需要决定的问题

1. **声明模型下如何防止"习惯性越门"？** 本评审的判断是：靠首轮回复结构 + 交付时回放原话，而非门禁。这需要产品层面的取舍确认。

4. **是否保留四件套强耦合安装？** §5.2 显示它已产生版本不一致问题；拆分为"核心 + 可选"可能更稳，但会改变 `skills.json` 的依赖描述。

## 10. 一句话总结

"必须用这么多方法"是个假前提。真实的因果是：把**过程合规**当成功判据、把**可写文件**当信任锚，两次选择叠加，生成了一台服务评测台和审计的机器。它的成本落在每一轮的 Agent 注意力上，它制造了新的协作失败模式，它最强的保证不覆盖真实发生的失败，而它最严的门禁恰好加在最可逆的决定上。

**要做的不是继续补，而是删到只剩那条交付不变量，然后把人的判断还给人。**
