# 任务交互合同

交互合同在结构候选之前形成，用来约束信息架构、状态与范围，不规定配色、字体、构图或组件外观。它按用户任务组织，不按 SaaS、教育、电商等行业名称套页面模板。

合同写进同一份 `surface-brief.md`，不新增项目产物。简单展示页或局部修改只保留适用项；新建、主流程或信息结构变化必须覆盖完整任务和明确排除项。

## 四级约束

| 等级 | 判定 | 后续处理 |
| --- | --- | --- |
| `required` | 没有它就无法完成已确认任务、得到可观察结果，或无法控制已确认风险 | 必须进入结构、实现和检查 |
| `recommended` | 由频率、数量、设备、内容或可逆性推导出的较优做法，但可能被更具体的项目事实覆盖 | 采用，或记录有依据的偏离理由；推荐不是用户决定 |
| `confirm` | 会改变范围、业务语义、角色权限、数据生命周期、费用或风险 | 交给 `site-brief` 确认；未确认前不得表现为真实能力 |
| `excluded` | 创作者明确排除，或已确认不进入本轮 | 页面、导航、文案、状态和模拟数据都不得暗示存在 |

行业资料、竞品和通用最佳实践只能提出 `recommended` 或 `confirm`，不能单独把能力升级成 `required`，也不能推翻 `excluded`。每条外部做法先回答：它服务哪条已确认任务？依据来自哪里？会不会新增对象、角色、状态、数据或外部服务？前两问答不上来就丢弃；第三问为“会”就标 `confirm`。

## 形成合同

从 brief、真实内容、活跃工程和用户材料提取以下内容。只记录会改变页面组织、操作或状态的条件，不为填模板制造需求。

1. **任务类型：** 用自然语言写用户要判断、查找、创建、处理、学习还是咨询什么，不把类型映射成固定页面集。
2. **核心对象与生命周期：** 对象从哪里出现，经过哪些已确认状态，成功后去哪，失败或取消时保留什么；状态语义不明就标 `confirm`。
3. **频率、数量与时长：** 偶尔一次还是每天重复，处理一条还是几百条，用户需要扫读、比较还是沉浸完成；没有事实就不假定“高效工作台”。
4. **设备与场景：** 各设备上用户能看什么、做什么，是否单手、触屏、弱网或大屏；窄屏按任务重组，不把桌面布局机械压缩。
5. **风险与可逆性：** 写入、删除、发布、付费、隐私、未成年人数据和外部服务的后果；高风险未知必须确认。
6. **导航与工作区原则：** 首屏先支持哪个判断或动作，对象如何切换，当前位置和未完成输入如何保留；导航深度由任务跨度决定，不因“后台”默认增加侧栏和首页。
7. **完整 Flow：** 至少写清起点、主路径、成功、失败恢复、中途退出和再次打开。不存在的状态标 `not_applicable` 并说明理由，未知状态标 `confirm`，不能静默省略。
8. **中国本地化条件：** 根据真实受众核对中文术语、中文输入法组合态、日期时间、数字金额、地址电话、触屏和常见弱网场景。微信、短信、二维码、支付、实名、备案或数据收集属于能力或风险，不是“中国用户习惯”的自动默认值。
9. **明确排除项：** 逐条写入 `excluded`，防止候选、旧稿、组件库或竞品把它们带回来。

## 从任务推导，而不是从行业复制

以下只是推导示例，不是行业模板：

| 已知任务条件 | 可形成的 `recommended` | 不能顺手推导 |
| --- | --- | --- |
| 高频、批量、连续判断对象 | 稳定列表/详情关系、当前位置、处理后反馈、较短操作路径 | KPI 首页、批量操作、快捷键、自动分配 |
| 学习者完成一个练习并获得反馈 | 当前任务突出、输入保留、结果可理解、返回后连续 | 账号、积分、证书、排行榜、长期进度 |
| 用户浏览内容后做一次现实决定 | 关键事实前置、比较依据清楚、主要行动随手可达 | 注册、支付、评价、个性化推荐 |
| 操作不可逆或后果较大 | 后果说明、明确确认、结果凭据和可行恢复路径 | 审计中心、复杂权限或审批链 |

如果某个做法只因为“同类产品都有”，它最多是 `recommended`；一旦引入新的业务含义或范围，就升级为 `confirm`，而不是升级为 `required`。

- 导航与工作区原则：

同一事实只写一次，再由 ID 映射到结构、纵向切片和检查矩阵。`recommended` 可以有依据地偏离；`confirm` 若会改变核心结构、范围或风险，先回到 `site-brief`，不能用体验稿替用户决定。
