# 回答一个问题的可见实验

体验稿用最低成本回答一个明确未决问题，不提前开发半个产品。开始前至少知道最终用户、首版任务、代表内容、主要设备和高风险边界。

## 选择成果

| 未决问题 | 成果 | 记录 |
| --- | --- | --- |
| 信息怎么组织、什么最重要 | 低成本结构候选 | 确实比较多个时 `confirm-structure` |
| 同一结构如何表达 | 完整视觉候选 | `confirm-visual` |
| 操作顺序、状态或规则 | 可点击流程/状态演示 | 业务决定交回 `site-brief` |

一个完整候选已经同时回答结构和视觉，或用户明确委托 Agent 选择时，不为了流程再制造第二轮。

## 结构候选

信息拓扑尚未确定时先用草图、线框或最小 HTML。候选必须使用相同真实内容、状态和相近视口，在顺序、主次、密度、导航或交互模型上真正不同；不要先做三份精美页面再调整信息架构。

用户选择结构后只记录结构决定，视觉仍未决定。结构发生实质变化会使基于旧结构的视觉候选失效。

## 视觉候选

固定结构、任务、内容和状态，再比较 2～3 个 direction。每个候选有独立的证据、母题、构图和项目签名；grammar 用于一致落实，不能把同一方向换三套颜色当三个候选。已有明确参考/系统或全权委托时可以只给一个完整推荐。

模板可以用于快速接线，但只能在任务合同和 direction 之后进入 patterns。体验稿中采用模板时也要删掉未确认字段/状态，替换真实内容和 grammar，并记录 adaptation。

## 流程与状态演示

当对话不足以判断操作时：

1. 页面说明本轮要回答的问题；
2. 用业务语言显示当前状态；
3. 允许用户自由操作，而不是只能沿演示脚本点击；
4. 覆盖正常、关键边界和应被阻止的操作；
5. 每次操作后显示发生了什么、保留了什么。

默认使用内存与明确标记的示例数据，不连接正式后端、账号、支付或外部写入。状态间的列表、详情、计数、筛选和未保存内容必须一致。

## 可丢弃与演进

体验稿不需要完整工程抽象，但必须可运行、可判断。包含生产数据和完整交互的稿件已经接近成品，不要形式化重写。

确认后默认 `evolve`：保留已确认结构、样式与交互，替换模拟数据、补正式边界、删除候选切换器。只有原技术形态无法承载正式要求时使用 `rebuild`，并写具体原因。交给 builder：

```text
问题与选中成果
DesignPacket 路径
核心页面、状态和主行动
direction / grammar / patterns 与 adaptations
evolve | rebuild 及理由
正式入口建议
保留 / 替换 / 删除
模拟与缺失范围
```

## 展示前验证

实际打开目标桌面与手机视口，先修复明显任务、布局和状态问题。使用 `check-render.mjs` 记录机械证据；方向、构图和项目特异性按 review protocol 独立判断。没有浏览器时可以生成稿件，但必须将视觉与交互写为 `not_run`。

文件存在、截图存在和“挺好看”都不是开发授权。正式源码仍由 `site-builder` 修改。
