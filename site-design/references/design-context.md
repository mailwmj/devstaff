# 从项目事实形成设计方向

页面类型、行业名称和 token 配方都不能替代设计判断。先建立当前页面的事实，再决定结构与表达；只在事实不足以支持核心结构时调用 `site-brief`。

## 1. 判断工作深度

- **新建、整体改版、核心流程或信息结构变化：** 使用本文件的完整方向合同。
- **已有成熟设计系统或明确参考：** 继承已确认方向，只记录当前页面的任务、结构差异和例外。
- **局部色值、间距、文案或单个控件：** 不重做方向合同，不重新选择 palette、字体或页面类型。
- **只读审查：** 从实际页面提取可见事实；缺少的产品或品牌依据标为 `not_run`，不启动访谈。

## 2. 页面事实

只收集会改变本轮成果的信息：

```text
使用者：谁在什么情境下打开页面
主任务：此刻必须完成的一个动作或判断
业务对象：正在阅读、比较、编辑或处理什么
真实内容：已有文案、数据形状、图片和数量级
状态：已确认可达的正常、空、错、保存或边界状态
后果：操作是否可逆，是否涉及费用、权限或敏感数据
频率：一次性、偶尔或高频连续使用
设备：主要视口、输入方式和环境
已确认能力：登录、角色、支付、同步、外部服务等
继承依据：现有设计系统、代表页面、品牌与参考
```

行业词只用于帮助想到遗漏。例如“CRM”可能提示跟进历史和权限风险，但不能证明项目需要团队、报表、自动化或固定 Sidebar。

## 3. 范围防火墙

采用任何参考、行业经验或常见模式前先分类：

- `within_scope`：用户、brief、现有代码或已确认流程已有依据，可以进入本稿。
- `alternative_only`：只是一种结构取舍，可以展示但不能写成既定需求。
- `requires_confirmation`：会新增页面、角色、状态、持久化、登录、支付、外部服务或高风险后果，交给 `site-brief`；只读审查标为依据不足。

**行业常见不能单独证明能力属于首个可验证版本。** 示例内容只能帮助判断结构，必须显式标注；不得把模拟内容写成用户事实。

## 4. 冲突优先级

从高到低处理：

1. 安全、隐私、无障碍和高风险门禁；
2. 已确认首版范围、真实项目事实和用户明确要求；
3. 已选方向、成熟设计系统和参考继承边界；
4. 前置事实成立的条件性 UX 机制；
5. 页面类型或行业先验；
6. gallery、配方、示例和组件范例。

会改变核心体验或范围的冲突调用 `site-brief`；低风险冲突采用范围最小、最可逆的答案并标明假设。不能让措辞更强的示例覆盖更高优先级事实。

## 5. 简短方向合同

首次视觉实现前，用紧凑内容确定：

```text
问题：本稿要验证什么
事实：哪些项目事实实际影响设计
路径：用户先看什么、判断什么、做什么
方向：页面命题、首屏结构和真实素材主角
反默认：该类别最容易生成什么，本项目为何不照搬，用什么替代
完成：在哪些页面、状态和视口看到什么才算成立
```

方向合同是思考与交接检查点，不是固定页面 section，也不要求向创作者展示长篇设计术语。无法写出项目特定的“反默认”和替代答案时，说明方向尚未形成，不进入 token 选择。

## 6. 页面职责只用于召回

可用以下词帮助查找相关问题，但允许组合，且不直接决定布局：

- `persuade`：理解、信任、转化；
- `operate`：高频处理、管理、审批；
- `analyze`：比较、诊断、预测；
- `browse-compare`：发现、筛选、比较；
- `transact`：预约、提交、支付、确认；
- `read`：连续阅读和查找；
- `create-edit`：创作、编辑和恢复；
- `communicate`：消息、评论和协作。

知识只应补充待考虑的问题、状态、后果和验证方式。不得因页面职责或行业标签自动选择固定导航、屏幕数、CTA 位置、颜色、字体或组件库。
