# 展示前设计评审与复验

制作分支在向创作者展示前执行；只读分支使用相同观察方法，但只报告、不修复。评审必须查看实际渲染，不能以代码阅读、构建成功或截图文件存在代替。

## 1. 固定检查条件

先记录：页面、代表内容、状态、视口、主题、参考条件和本稿要回答的问题。比较方向时保持内容和视口一致；比较参考时保持可见状态、裁剪和密度尽量一致。

至少查看主要视口和一个最可能暴露问题的窄视口。只检查本轮范围内真实需要的状态，不为小型离线工具虚构服务器故障或权限体系。

## 2. 三路分别判断

### A. 设计判断

- 主任务是否获得正确视觉重量；首屏是否先给用户需要的答案；
- 构图、排版、色彩、素材、密度和动效是否共同兑现方向；
- 页面是否像真实产品，而不是悬空组件 demo；
- **反默认检查：** 是否无依据地回到该类别最常见的 Hero、KPI 卡、等宽卡片、Sidebar＋Table 或风格标签；
- **替换检查：** 换成惯用字体、常见配色或标准模板后若几乎不影响表达，哪些决定仍未形成；
- **项目标志检查：** 至少指出一个来自业务对象、内容、结构或交互的项目特定表现。它不必是装饰，也不得为了独特妨碍熟悉任务。
- **工艺三查：** 按 [排版](typography.md) 核对角色分配、字阶、行高、行长、标点与数字对齐；按 [色彩与素材](color-and-material.md) 核对颜色来源、语义角色分布、素材出处与许可、缺口是否如实；按 [构图与节奏](composition.md) 核对视觉重量与任务一致、尺度对比可感、边缘与基线对齐、留白是构图、极端内容各自设计、细节签名服务内容。缩小到 25% 看一次：仍有重心与结构才算构图成立。

采用类别标准不是失败；无法说明它为何适合当前事实才是惯性。**设计判断 `passed` 需要上述四组检查都实际做过并留下依据**——只看了一眼截图就写 `passed`，属于证据纪律问题。

### B. 任务与状态

实际完成核心任务，并观察操作后的语义结果：

- 主要行动、取消、返回和恢复是否清楚；
- 表单校验、保存反馈、空/无结果和错误是否可达；
- 编辑后派生计数、筛选范围、状态标签和详情是否同步；
- 切换对象、关闭覆层或返回时，未保存内容是否会静默丢失；
- 模拟状态是否前后一致，是否让用户误以为真实能力已完成；
- 决策所需依据在各视口都可找到。

“按钮可点”不等于流程通过；操作后的数据、状态和下一步必须符合本稿声明。

### C. 机械检查

- 横向溢出、裁切、遮挡、滚动陷阱和固定元素覆盖；
- 中文长标题、按钮、导航、标点、中英数字混排和字体回退；
- 实际相邻色对、焦点、键盘顺序、触控尺寸和图标名称；
- 标题层级、图片 alt、控件 label、减少动态效果；
- 控制台错误、失败资源和目标入口。

至少执行并记录以下可观察断言，而不是只凭截图印象：

- **布局**：`document.documentElement.scrollWidth <= document.documentElement.clientWidth`（没有横向溢出）；核心固定/粘性行动的 `getBoundingClientRect()` 完整落在目标视口内；关键证据和主行动在目标窄屏仍有可见或可展开路径；
- **字面**（读渲染后的 computed style，不读源码声明）：正文与标签的 `font-size` 不低于下限，且承担主要阅读的文字不在 12px 档；连续正文的 `line-height` 与 `max-width` 落在 [排版](typography.md) 的区间内；中文标题的 `letter-spacing` 不为负值；数字类单元格使用等宽或表格数字；
- **色彩**：对渲染后的**实际相邻色对**（文字与它真正落在的背景）计算对比度并记录数值，不用 token 表里的相邻关系代替。半透明、图片叠层与动态状态不在自动范围内，须人工查看并说明；
- **触控**：可点击元素的渲染尺寸不低于项目的最小触控尺寸（紧凑密度下同样成立）；
- **运行**：控制台没有运行错误，无失败资源和缺失入口。

断言失败即为 `failed`，不能以“用户可以横向滚动”“实际看着还行”或“截图大致正常”替代修复。**读源码得到的字号与颜色不算证据**——层叠、媒体查询、`clamp()` 和主题变量都会改变最终值。

机械检查没有发现问题，只能说明已检查项目未触发，不能推出设计优秀。

## 3. 窄屏保真

不要把桌面版简单压成一列或通过 `display:none` 通过响应式检查。逐项确认：

1. 主任务和主要行动仍可达；
2. 支撑判断的价格、时间、状态、风险和解释没有消失；
3. 隐藏内容确实是冗余表达，而非功能或证据；
4. 覆层可关闭、提交不被遮挡；
5. 宽表、长列表和媒体有明确的重组或局部滚动策略。

任何在窄屏删除的信息都要能回答“为什么不影响用户完成任务”。

## 4. 修正循环

制作分支先列出最可能让创作者觉得“不够好或不好用”的问题，修复影响主任务、构图、真实性、状态一致性或窄屏的主要问题，再用相同条件重新渲染。不能把第一次看见的问题留给创作者发现。

若连续两轮没有新证据或进展，停止无界打磨，返回 `blocked` 或把细微偏好列为后续建议。

## 5. 记录结论

三路分别记录 `passed | failed | not_run | not_applicable`：

```text
检查轴：design | task_state | mechanical
页面 / 状态 / 视口：
结论：
证据：实际操作、截图或限制
发现及任务影响：
修复后证据（制作分支）：
```

`passed` 只覆盖实际查看和操作的条件。只读审查缺少 brief 或确认方向时，通用设计与机械问题仍可报告，但方向匹配和跨页一致性应为 `not_run`。
