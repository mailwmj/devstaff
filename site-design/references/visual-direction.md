# 从项目事实推导 Direction

Direction 回答“为什么这个项目这样表达”，不是风格名、规范或 token。新建、整体改版和新视觉表达使用本方法；局部样式沿用现状；只读审查核对已声明 direction 是否兑现。

## 1. 选择来源

来源不是继承链，可以与任意 grammar/pattern 组合：

- `existing`：活跃设计系统、品牌资产和代表页面提供项目自身方向；
- `reference`：用户指定参考提供可观察的主次、比例、材料或节奏，必须写借鉴边界；
- `project-derived`：从真实业务对象、内容、数量、变化、使用环境和行为后果推导。

规范只可能是 grammar，模板只可能是 pattern。它们不能填进 direction.source。

## 2. 五步推导

1. **内容事实。** 指出真正承担表达的一个对象、数据、时间关系、实物或原文。去掉它后页面若几乎不变，选错了主角。
2. **视觉世界。** 找到主角所属的材料、媒介和环境。用户素材/现有产品是 `measured`，对象属性与明确参考推导是 `derived`，受众偏好猜测是 `inferred`。`inferred` 不能单独支撑方向。
3. **母题。** 从视觉世界收敛一个贯穿页面的形式决定。它必须帮助一类信息被看见，并能在现有技术条件下实现。
4. **构图命题。** 用一句话写主次关系，以及它靠尺度、位置、对比、留白或运动如何成立。删掉该手段后首要内容应发生变化，否则命题不可证伪。
5. **项目签名。** 选择一处做到更深的细节，服务真实对象或状态，并能在多个页面复用；其余地方保持克制。

然后再用 [排版](typography.md)、[色彩与素材](color-and-material.md) 和 [构图](composition.md) 落实，不让这些实现参数反过来产生方向。

## 3. 两个检查

**替换检查**：把项目名、行业和内容换成另一个项目，母题、构图和签名是否仍完全成立？如果是，它只是通用装饰。

**信息检查**：每个形式决定具体帮助谁看见、判断或操作什么？答不出就删除，不用“高级、科技、电影、杂志”等不可证伪词补洞。

熟悉模式可以使用。反默认的要求不是故意猎奇，而是明确说明它为何适合当前事实；无法说明的默认卡片、巨大欢迎标题或无意义装饰才是问题。

## 4. 候选

只有用户确实需要比较时才做 2～3 个候选。固定同一任务、信息架构、真实内容、状态和素材；候选在母题、构图或项目签名上有实质差异。把候选的配色和字体互换后差异仍应成立。

候选名称只是沟通摘要。每个候选说明：事实依据、最突出什么、牺牲什么、对素材/实现/无障碍的要求。给推荐但等待用户选择；已有明确参考、成熟系统或全权委托时可以只有一个有依据方向。

## 5. 交接

写入 surface brief 和 DesignPacket：

```yaml
direction:
  source: project-derived
  evidence:
    - source: 访谈原文
      observation: 每段都有说话者与采集日期
      confidence: measured
  motif: 逐段展开的口述记录
  composition: 正文为主轴，人物与时间退居侧线
  project_signature: 每段保留说话者与采集日期的边注
```

素材记录实际来源、用途、裁剪和真实性缺口即可；不做许可门禁。Direction 不写 `spec_id`、模板名或行业速查结果。
