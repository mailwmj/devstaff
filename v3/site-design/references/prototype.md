# 回答一个问题的可见实验

体验稿用低成本成果回答一个明确问题，不是提前开发半个产品。开始前至少知道核心用户、场景、首版任务与范围、代表内容、主要设备和高风险边界；否则调用 `site-brief-v3`。

制作前在 [页面设计合同](surface-brief.md) 记录本轮事实和原型覆盖；展示前标明哪些已演示、模拟或未覆盖。原型不能反向创造正式范围。

## 1. 选择实验类型

| 未决问题 | 成果 |
| --- | --- |
| 页面如何组织、什么最重要、内容如何表达 | 页面方向；默认一个推荐，真实取舍存在时提供对照 |
| 整体气质、排版、色彩、边界、密度和素材表达 | 同一页面上的视觉方向 |
| 操作顺序、可达状态或业务规则 | 流程/状态体验稿 |

一个体验稿只承担一个主要问题。外观和流程都不确定时，先回答最阻塞后续的那个问题。

## 2. 形成完整页面方向

### 结构

默认只做一个接近成品的推荐核心页面。只有不同结构会实质改变主任务、信息优先级或高风险取舍时，才做两个足以比较的方向；第三个只在它回答新的重要问题时出现。

多个结构方向必须：

- 使用相同业务内容、状态和相近视口；
- 在信息拓扑、内容顺序、主要操作、密度、强调或交互模型上真正不同；
- 统一字体和颜色后，差异仍然成立；
- 包含至少一个来自真实业务对象、内容或行为的项目特定表现；
- 只做到足以判断，不扩展全部页面；
- 写入隔离体验目录，不替换正式路由和源码。

多方向可以在同一入口使用 `?direction=a|b` 和轻量切换条。切换器要明显区别于页面设计，并从正式实现移除。

### 视觉

结构形成后，按 [视觉方向](visual-direction.md) 推导母题、视觉世界、色彩来源、字体角色、构图命题和细节签名。候选必须在母题层不同，而不是同一页面换配色。

如果项目事实已经支持一个明显更合适的方向，直接推荐它，不为凑数制造第二稿。以下情况才提供对照方向：

- 两种表达会真实改变内容主次或信任姿态；
- 用户明确要比较；
- 现有品牌与参考之间存在无法自行消解的冲突。

每个方向说明依据、可见做法、突出什么和牺牲什么。做交换检查：互换候选的配色和字体后，如果差异基本消失，它们不是两个方向。

用户最终确认一个**完整方向**，同时包含任务、范围、结构和视觉。v3 不把结构、视觉和开发授权拆成三道默认门；结构发生实质变化时，先更新视觉方向，再重新确认整个方向。

## 3. 流程或状态体验稿

当文字不足以判断操作顺序、状态转换或业务规则时，制作一个轻量演示：

1. 用一句话说明要回答的问题；
2. 用业务语言显示相关状态，不只展示 JSON；
3. 提供少量自由操作；
4. 提供正常流程、关键边界和应被阻止的操作；
5. 每次操作后显示发生了什么和当前状态。

默认状态留在内存，使用真实或明确标注的示例内容。不连接正式数据库，不实现登录、支付或真实外部写入。状态演示还要核对派生计数、筛选、详情与列表同步、未保存内容、取消、返回和恢复。

## 4. 保持可丢弃

体验代码只需可运行和可判断，不为其建立完整抽象、持久化和测试。不得因为已经写了代码就视为正式实现。

确认后，在 `.v3/design/surface-brief.md` 中记录：

```text
本稿回答的问题
核心页面、状态与主行动
选定的完整方向与用户原话
方向来源与项目依据
母题、色彩来源、字体角色和构图命题
体验稿路径
素材来源、许可和模拟范围
正式实现必须补齐的内容
实际查看的页面、状态和视口
仍未关闭的发现与限制
```

交给 `site-builder-v3` 前说明体验稿应当演进还是重写。补全内部实现规格不需要用户再次确认；只有出现新的高影响方向或风险决定时才重新确认。

## 5. 完成条件

成果必须实际可见，目标视口已经查看，模拟和缺失范围已经说明。展示前按 [工艺审查](craft-review.md) 分开检查设计、任务状态和机械问题，集中修正后用相同条件复验。

文件存在、等待超时、构建成功或一句含糊的“还行”都不能自动构成方向确认。需要用户决定时，只展示当前真正影响结果的一个取舍。
