# 页面设计合同

这是 `site-design-v3`、`site-builder-v3` 与 `site-check-v3` 共用的设计接口。方向、实现和验收共享这一份事实，不另写互相漂移的规格。它是按需展开的专业模板，不是要求用户理解或逐项确认的流程清单。

复制到项目的 `.v3/design/surface-brief.md` 后填写。填写深度随任务变化：

- **quick：** 不创建合同；只检查和修改受影响项。
- **guided：** 填写本轮问题、项目事实、设计推导、选定方向，以及适用的页面、响应式、状态、素材和验收标准。
- **strict 或复杂产品：** 补全所有适用部分及风险证据。

不适用字段直接删除，不为完整感凑内容。体验稿前形成方向部分；方向确认后在同一文件补全实现规格。

## 首版承诺 × 原型覆盖

制作前从 brief 每条已确认“包含”建立引用；展示前按实际体验稿补判定，正式交接前逐条核对。使用既有编号或文件/章节/精确条目引用，不从原型现有控件反推首版，也不复制一份范围规格。

| 来源引用 | 可观察结果 / 验收条件 | 原型位置与覆盖判定 | 正式实现必须补齐 | 交接目标 ID |
| --- | --- | --- | --- | --- |
| `BR-01` 或精确条目引用 |  | `covered | simulated | missing`；页面/控件/状态及证据或限制 |  | `IC-* / CP-* / VA-*` 等适用 ID |

`covered` 仅表示本稿已实际演示该条件，不代表正式能力完成；`simulated` 写明替代的规则、数据或服务；`missing` 写清成品必须补什么，不能将承诺默默排除。例如“卖出一次可减多个”的体验稿只有“卖1”，对多件条件仍是 `missing`，不能用“卖出功能已覆盖”吞掉它。原型保持轻量，不要求为消除 `missing` 提前实现全部业务或持久化；无法确定补齐方向且会改变范围或风险时才回到对应决定。

交接目标在正式实现规格补全时填写。所有未覆盖或模拟的承诺均有正式补齐事项和目标后，才算覆盖交接完整；再次打开、持久化等无可见控件的承诺也要逐条保留。明确排除项沿用任务交互合同，不放进原型导航、占位控件或文案。

## 设计推导

- **用户路径：** 用户先看什么、判断什么、做什么？
- **首屏命题：** 这页最先让用户理解的一个事实是什么？
- **真实素材主角：** 哪个对象、数据、文案或图片承担主要表达？
- **类别默认：** 如果按这个类别最常见的生成式答案来做，会是什么？
- **反默认原因：** 哪些项目事实要求不采用它？
- **替代结构：** 用什么信息拓扑、顺序、密度、强调或交互替代？
- **明确不做：** 本轮拒绝哪些页面、功能或视觉表达？

## 视觉方向

按 [视觉方向](visual-direction.md) 推导。每一项都要能回到项目事实；写不出母题来源时方向尚未形成，不要用配色或字体填空。

- **内容事实：** 哪一个对象、数据、文案或素材承担表达（去掉它这页还剩什么）
- **视觉世界：** 来自什么材料、媒介或环境；证据等级 `measured | derived | inferred`
- **母题：** 贯穿全页的那一个形式决定；换一个产品名是否还成立（成立＝不是母题）
- **色彩来源：** 从什么采样、收敛成哪些语义角色；见 [工艺审查](craft-review.md)
- **字体角色：** display / 标题 / 正文 / UI / 数据各用什么、为什么；见 [工艺审查](craft-review.md)
- **构图命题：** 主次关系 + 它靠什么成立（尺度 / 位置 / 对比 / 留白 / 运动）
- **细节签名：** 哪一处做到 120%，它服务什么内容
- **素材与许可：** 来源、性质、许可、用途与裁剪；缺口有哪些

## 对照方向（仅在真实取舍存在时）

默认形成一个完整推荐方向。只有不同表达会改变内容主次、信任姿态或关键体验，或用户明确要求比较时，才增加对照方向；第三个方向必须回答新的重要取舍。向用户展示时使用普通语言，不暴露 recipe、palette、typography 或 token 等内部标签。

需要比较时，候选使用同一组内容、状态和相近视口，并在母题层真正不同。通过 [工具链](design-toolchain.md) 扩展候选后仍须由项目事实筛选。完成后做交换检查：互换任意两个候选的配色和字体，如果差异基本消失，它们只是换肤，应回到方向推导。

| 候选 | 匹配依据 | 母题 | 视觉世界 | 构图命题 | 突出 / 牺牲 | 实现 / 无障碍风险 | 结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `方案一` |  |  |  |  |  |  | `pending` |
| `方案二` |  |  |  |  |  |  | `pending` |
| `方案三（按需）` |  |  |  |  |  |  | `pending` |

- **交换检查结论：** 任意两候选互换配色与字体后，差异是否仍然成立？理由是什么？
- **结构差异证据（每个候选都必须填写）：** 主布局容器、核心组件形态、信息密度、首屏视觉重心。只写色板、字体、阴影或风格名视为换肤反模式，不能确认视觉。
- **行业 cue 分类：** `within_scope | alternative_only | requires_confirmation | discard`；行业名称本身不算上下文证据。
- **推荐项及理由：** 推荐不是确认，等待创作者选择。
- **候选不来自：** 无依据的风格标签、配方目录的相邻选项、同一母题的三种强度，或随机注入的大胆款。

### 使用边界

方向部分必须在第一次视觉实现前形成；正式实现规格在完整方向确认后、正式开发前补齐。候选满足 `required`、不暗示 `excluded`，对 `recommended` 的偏离写明依据；会改变核心范围或风险的 `confirm` 交回 `site-brief-v3`。无法写出项目特定的反默认、母题来源和替代结构时，先补事实，不用配方、色板或风格标签填空。用户只确认一次完整方向；结构发生实质变化时，先更新视觉方向，再重新确认整个方向。内部规格补全不新增用户门禁，但适用字段缺失时不得把猜测转移给实现者。
