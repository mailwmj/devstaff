# 渐进式建站：路由与门禁

这份文件告诉你：处理网站相关请求时**先用哪个 Skill、必须停在哪里**。它写给 Agent，不是写给用户的说明书。

用户是**没有编程背景的中文用户**。他不会说出 Skill 名称，通常只说"帮我做个网站""这页我想改改""你帮我看看哪儿有问题"。路由由你完成，不要让他选择流程、阶段或技术栈。

---

## 一、动手之前

1. **先取四个判据，再决定走哪条路。** 有 `.site/state.json` 时，门禁工具 `show` 一次就能取回全部四项，不要凭记忆或猜测：
   - **M1 工程**：无工程 ｜ 有工程未交付 ｜ `stage=delivered`
   - **M2 门禁位置**：`stage` 与 `concept_confirmed` / `structure_confirmed` / `visual_confirmed` / `development_authorized`。`structure_required=true` 而 `structure_confirmed=false` 时，用户只选了页面结构，**视觉风格还没确认**。结构数没声明时按多结构兜底（fail-closed）：只给一个结构必须显式声明 `--structure-directions 1`
   - **M3 运行态**：`lease.role` 是 writer 还是 checker 在持锁；`writer_release` 是否存在且 `release_matches_current_source=true`
   - **M4 高风险未决**：是否已有未决的登录／多人权限、云端或共享数据、未成年人数据、付费、第三方账号或密钥、公开部署

   这四项**每一项都可能改变第二节要走的路线**，不是可选参考。状态与用户措辞冲突时以状态为准；没有状态记录时，按第二节的表格判定该不该建。
2. **说清本轮走哪条路。** 用普通人能懂的短句说明你打算做什么、会停在哪里，让用户可以当场纠正。不要复述本文件或列出阶段名。
3. **命中即转交。** 本文件只负责"谁接、停在哪"，不重复任何 Skill 的内部流程；转交后按那个 Skill 的 `SKILL.md` 执行。
4. **只读状态，绝不写状态。** 项目状态一律由 `site-brief` 的 `scripts/state.py` 写入。不要用编辑工具改 `.site/state.json`、`.site/lease.json` 或 `.site/checks/`；状态细节按第五节的状态协议读取。

---

## 二、入口路由

| 用户想要 | 进入 | 越过即错（停位） |
| --- | --- | --- |
| 新建网站或应用、整体改版、动主流程／导航／信息结构 | `site-builder` → 先经 `site-brief` | 在 `concept_confirmed=true` 被记录之前：**不得**调用 `site-design`、**不得**初始化工程、**不得**创建实施计划、**不得**写正式源码 |
| 明确只要"把需求想清楚"，说了"先不要做""先别写代码" | `site-brief` | 停在协作回执。**不得**制作体验稿、**不得**开发。`ready` 只表示首版方案已确认，**不代表**视觉确认或开发授权 |
| 要"先看看"效果、要视觉方向、只分析截图／参考、只要设计评审 | `site-design` | 在 `visual_confirmed` 被记录之前：**不得**进入正式开发。视觉确认本身**不构成**开发授权。本轮让用户比较过多个**结构**时，他们选定结构只完成第一步：必须再在同一结构上给出风格方案（默认两个），风格那句才算 `visual_confirmed` |
| 不确定操作顺序或状态流转，要"做个能点的试试" | `site-design` 流程体验分支 | 停在流程确认。**不得**连接正式数据库、**不得**把流程被认可当成 `visual_confirmed=true` |
| 只要验收／检查，问"哪里有问题"（**没有**说修复），**且 M3 干净**（无自有 Writer 在跑、指纹已冻结） | `site-check` | 停在报告。**不得**修改源码、**不得**写协作状态、**不得**宣布交付 |
| 同上，**但 M3 显示自有体验稿／开发服务仍在跑，或源码指纹尚未冻结** | `site-builder` 先交接，通过后才交 `site-check` | 停位：停止自有服务 → 登记正式服务的 owner／PID／端口／根目录 → `handoff` → `start-verify` 通过。**不得**在 Writer 子进程仍运行时启动 Checker，**不得**复用归属未确认的端口 |
| 说了"检查并修复""把它修好"，或要改文案／颜色／间距、修 bug | `site-builder` | 改动范围以用户指出的问题为界：**不得**借机重做需求、重选视觉或扩大范围。**不得无限重试**：连续两轮复验没有新证据或进展时，用 `block` 记录恢复条件，并如实告诉用户"卡在哪儿、还缺什么" |
| 回来说"继续"／"接着上次"／"做到哪了"（无状态时按上面各行判定） | 读 M2，在**未通过的那道门禁**恢复 | 停在下一个未确认的门禁。**不得**因为"上次已经开始了"就跨过未确认的门禁继续 |

**"验收"两个口径靠 M3 区分，不靠措辞。** "帮我验收一下"这类话在两种状态下义务相反：M3 干净时是只读检查；自有 Writer 还在跑时，先交接冻结指纹才允许 Checker 介入。**不要用句式猜**——先 `show`，再看 `lease.role` 与 `release_matches_current_source`。

**要不要建 `.site`，由入口意图 × M1 联合判定，不能只看"有没有状态"：**

| 入口意图 | M1 无工程／无状态 | M1 有状态 |
| --- | --- | --- |
| 新建、整体改版（新项目） | **要**建初始状态 | 沿用，按 M2 恢复 |
| 局部修改、Bug | **不建**，直接改 | 沿用，不重走门禁 |
| 第三方项目只读审查／验收 | **不建**，且不得开启需求访谈 | 沿用；缺依据时标 `not_run` |

**局部修改与 Bug 不建 `.site`、不重走方案和视觉门禁**；但"不重走门禁"不等于"没有门禁"——它们仍受第四节三条红线约束。

**只读设计评审**（对别人或第三方项目）额外受三条约束：不调用 `site-brief` 开启需求访谈、不创建 `.site`、不补造视觉依据；缺少既定方向或确认设计时，把"方向匹配"如实标为 `not_run`，只按通用质量规则报告发现。

## 三、近邻判别

- “帮我做个网站”进入 `site-builder → site-brief`；“只梳理/先不要做”进入 `site-brief`。
- “先给我看看效果”、截图/参考或视觉评审进入 `site-design`；“检查一下”进入 `site-check`，要求修复则由 `site-builder` 编排。
- 简短肯定按它直接回答的上一问及行动后果归属；结构、视觉和开发授权不能互相代替。无法判断时走更重的路径并补问。
- 局部文案/颜色/间距和可复现 Bug 走 `site-builder` 快速分支；核心范围或高风险事项变化时按状态协议重新确认。

---

## 四、三条红线

任何一轮、任何捷径下都不得越过：

1. **方案未确认**（`concept_confirmed=false`）→ 不制作正式设计、不进入正式开发。
2. **结构或视觉未完成** → 只能记录已发生的决定，不得推断开发授权或创建正式成果。
3. **没有合格凭据** → 不得宣布交付；检查矩阵、证据、源码指纹和 `not_run` 规则按第五节的状态/验证协议执行。
4. **核心范围或高风险事项变化** → 旧确认和交付结论失效，按状态协议重新确认。

## 五、协议来源

本文件只负责路由、停位和三条红线；命中入口后按需读取唯一的协议来源，不在这里复制内部流程：

- 术语与四类确认记录：[`CONTEXT.md`](../CONTEXT.md)
- 状态、原话、租约、交接和交付门禁：[`site-brief/references/state.md`](../site-brief/references/state.md)
- Skill 间回执与问题闭环：[`site-brief/references/context-contract.md`](../site-brief/references/context-contract.md)
- 页面设计合同：[`site-design/references/surface-brief.md`](../site-design/references/surface-brief.md)
- 检查档位、证据和 `not_run`：[`site-check/references/verification.md`](../site-check/references/verification.md)

Skill 的 `SKILL.md` 只补充本 Skill 的职责和执行顺序；发生冲突时，以状态工具和上述对应协议为准。

## 六、能力不足与交付

- 缺少浏览器、命令或可读会话记录时，按对应协议诚实记录 `not_run` 或 `agent-reported`，不得把声明说成验证。
- 交付前由 `site-builder` 按状态协议取得当前矩阵和 `consent_replay`；检查失败或源码变化时停止交付并回到修复流程。
- 交付消息只说打开方式、完成范围、已检查/未检查内容、数据位置和限制，不把内部协议术语展示给用户。

---

## 七、可以按需覆盖的部分

项目级或单个 Agent 的配置可以**追加**本文件之外的路由（例如本团队额外要求的 Skill），但：

- **第四节三条红线不可覆盖、不可放宽**；
- 覆盖内容不得与四个 `site-*` Skill 的 `SKILL.md` 冲突；冲突时以 `SKILL.md` 与状态门禁工具为准；
- 覆盖后请确认四个 Skill 仍都能被路由到——不要因为增删条目让某条路径失效。
