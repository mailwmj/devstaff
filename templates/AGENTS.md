# 渐进式建站：路由与门禁

这份文件告诉你：处理网站相关请求时**先用哪个 Skill、必须停在哪里**。它写给 Agent，不是写给用户的说明书。

用户是**没有编程背景的中文用户**。他不会说出 Skill 名称，通常只说"帮我做个网站""这页我想改改""你帮我看看哪儿有问题"。路由由你完成，不要让他选择流程、阶段或技术栈。

---

## 一、动手之前

1. **先取四个判据，再决定走哪条路。** 有 `.site/state.json` 时，门禁工具 `show` 一次就能取回全部四项，不要凭记忆或猜测：
   - **M1 工程**：无工程 ｜ 有工程未交付 ｜ `stage=delivered`
   - **M2 门禁位置**：`stage` 与 `concept_confirmed` / `structure_confirmed` / `visual_confirmed` / `development_authorized`。`structure_required=true` 而 `structure_confirmed=false` 时，用户只选了页面结构，**视觉风格还没确认**。结构数没声明时按多结构兜底（fail-closed）：只给一个结构必须显式声明 `--structure-directions 1`
   - **M3 运行态**：`lease.role` 是 writer 还是 checker 在持锁；`writer_release` 是否存在且 `release_matches_current_source=true`
   - **M4 高风险未决**：是否已有未决的登录／多人权限、云端或共享数据、未成年人数据、付费、第三方账号或密钥、公开部署

   这四项**每一项都可能改变第二节要走的路线**，不是可选参考。状态与用户措辞冲突时以状态为准；没有状态记录时，按第二节的表格判定该不该建。
2. **说清本轮走哪条路。** 用普通人能懂的短句说明你打算做什么、会停在哪里，让用户可以当场纠正。不要复述本文件或列出阶段名。
3. **命中即转交。** 本文件只负责"谁接、停在哪"，不重复任何 Skill 的内部流程；转交后按那个 Skill 的 `SKILL.md` 执行。
4. **只读状态，绝不写状态。** 项目状态一律由 `site-brief` 的 `scripts/state.py` 写入。不要用编辑工具改 `.site/state.json`、`.site/lease.json` 或 `.site/checks/`。

## 二、入口路由

| 用户想要 | 进入 | 越过即错（停位） |
| --- | --- | --- |
| 新建网站或应用、整体改版、动主流程／导航／信息结构 | `site-builder` → 先经 `site-brief` | 在 `concept_confirmed=true` 被记录之前：**不得**调用 `site-design`、**不得**初始化工程、**不得**创建实施计划、**不得**写正式源码 |
| 明确只要"把需求想清楚"，说了"先不要做""先别写代码" | `site-brief` | 停在协作回执。**不得**制作体验稿、**不得**开发。`ready` 只表示首版方案已确认，**不代表**视觉确认或开发授权 |
| 要"先看看"效果、要视觉方向、只分析截图／参考、只要设计评审 | `site-design` | 在 `visual_confirmed` 被记录之前：**不得**进入正式开发。视觉确认本身**不构成**开发授权。本轮让用户比较过多个**结构**时，他们选定结构只完成第一步：必须再在同一结构上给出 2～3 个风格方案，风格那句才算 `visual_confirmed` |
| 不确定操作顺序或状态流转，要"做个能点的试试" | `site-design` 流程体验分支 | 停在流程确认。**不得**连接正式数据库、**不得**把流程被认可当成 `visual_confirmed=true` |
| 只要验收／检查，问"哪里有问题"（**没有**说修复），**且 M3 干净**（无自有 Writer 在跑、指纹已冻结） | `site-check` | 停在报告。**不得**修改源码、**不得**写协作状态、**不得**宣布交付 |
| 同上，**但 M3 显示自有体验稿／开发服务仍在跑，或源码指纹尚未冻结** | `site-builder` 先交接，通过后才交 `site-check` | 停位：停止自有服务 → 登记正式服务的 owner／PID／端口／根目录 → `handoff` → `start-verify` 通过。**不得**在 Writer 子进程仍运行时启动 Checker，**不得**复用归属未确认的端口 |
| 说了"检查并修复""把它修好"，或要改文案／颜色／间距、修 bug | `site-builder` | 改动范围以用户指出的问题为界：**不得**借机重做需求、重选视觉或扩大范围。**不得无限重试**：连续两轮复验没有新证据或进展时，用 `block` 记录恢复条件，并如实告诉用户"卡在哪儿、还缺什么" |
| 回来说"继续"／"接着上次"／"做到哪了"（无状态时按上面各行判定） | 读 M2，在**未通过的那道门禁**恢复 | 停在下一个未确认的门禁。**不得**因为"上次已经开始了"就跨过未确认的门禁继续 |

**"验收"两个口径靠 M3 区分，不靠措辞。** "帮我验收一下"这类话在两种状态下义务相反：M3 干净时是只读检查；自有 Writer 还在跑时，先交接冻结指纹才允许 Checker 介入。**不要用句式猜**——先 `show`，再看 `lease.role` 与 `release_matches_current_source`。

**要不要建 `.site`，由入口意图 × M1 联合判定，不能只看"有没有状态"：**

| 入口意图 | M1 无工程／无状态 | M1 有状态 |
| --- | --- | --- |
| 新建、整体改版（新项目） | **要**建初始状态 | 沿用，按 M2 恢复 |
| 局部修改、Bug | **不建**，直接改 | 沿用，不重走门禁 |
| 第三方项目只读审查／验收 | **不建**，且不得开启需求访谈 | 沿用；缺依据时标 `not_run` |

**局部修改与 Bug 不建 `.site`、不重走方案和视觉门禁**；但"不重走门禁"不等于"没有门禁"——它们仍受第四节三条红线约束。

**只读设计评审**（对别人或第三方项目）额外受三条约束：不调用 `site-brief` 开启需求访谈、不创建 `.site`、不补造视觉依据；缺少既定方向或确认设计时，把"方向匹配"如实标为 `not_run`，只按通用质量规则报告发现。

## 三、近邻判别（最容易判错的地方）

| 用户这样说 | 判据 | 结论 |
| --- | --- | --- |
| "帮我做个网站" ／ "帮我想想做什么" | 有没有"只梳理""先不要做" | 前者 `site-builder` → `site-brief`；后者直接 `site-brief` |
| "先给我看看""让我看下效果" | 是否要求**看见** | `site-design` |
| "第二个好看""颜色不错""大概可以" | **这三类都不是授权**；并先判断用户选的是**结构**还是**风格** | 选的是完整页面 → 记录 `visual_confirmed`；比较的是页面组织方式（"列表+详情的那个"）→ 只记录 `structure_confirmed`，**风格还没确认**，必须再给 2～3 个风格方案。两者都**不得**写 `development_authorized=true`、**不得**创建实施计划、**不得**开始写正式源码——停下来问 |
| "是A没错""结构就按这个" | 用户回答的是哪一步的问题 | 只说明结构定了。**不得**记成 `visual_confirmed`，也**不得**直接进入开发；下一步是在这个结构上给风格方案 |
| "就按这个做""开始开发" ／ "细节你全权决定""你看着办" | 是否明确授权，以及是否触发高风险 | 前者才可写 `development_authorized=true`；后者在**低风险范围内**可采用推荐项连续推进。两者都**不覆盖**登录／多人权限、云端保存或共享数据、未成年人数据、付费、第三方账号或密钥、公开部署——遇到必须单独问 |
| "检查一下" ／ "检查并修复" | 有没有"修好" | 前者 `site-check` 只读；后者由 `site-builder` 编排 `site-check` 并在修复后重新交接复验 |
| "改个按钮文案" ／ "重做首页" | 是否动结构、导航、核心流程 | 前者 `site-builder` 快速分支；后者走 `site-design` |
| "原来是自己记账，现在要一家人登录共享" | 核心用户／角色／数据风险是否实质变化 | 先使旧的方案确认、结构确认、视觉确认、开发授权和交付状态**全部失效**（`reopen --scope-changed`），回到方案门禁重新确认 |
| "就改改样式／换个感觉，别的不动" | 动了**风格**还是**结构** | 只动风格：`visual_confirmed=false`，旧开发授权未明确覆盖时同时清 `development_authorized`，阶段回 `visual_review`。动了**结构**：`structure_confirmed=false` 且 `visual_confirmed=false`，阶段回 `visual_drafting`，必须重新给风格方案。已授权或已交付时先 `reopen --scope-changed` |
| 交付时念回原话，用户说"我没说过这个""这不是我的意思" | `consent_replay` 是否被本人否认 | **立即先 `reopen`**，再回到被否认的那道门禁重新确认。**不得**带着存疑的同意交付，也**不得**用"当时确实记录过"说服用户 |

判定不了时，**取更重的那条路**，并问用户一句；不要在方案里替用户决定，也不要因为"已经做了一半"就维持原路。

## 四、三条红线

任何一轮、任何捷径下都不得越过：

1. **方案未确认**（`concept_confirmed=false`）→ 不制作正式设计、不进入正式开发。
2. **只有结构选择或只有视觉选择** → 只能记录对应的那一项（`structure_confirmed` 或 `visual_confirmed=true`），**不得**推断开发授权、**不得**创建正式源码或实施计划。用户只比较过页面结构时，风格方案这一步还没发生。
3. **没有合格凭据** → 没有与当前源码指纹一致、且本轮阻断项全部 `passed` 的 `check_id` 时，**不得**宣布交付。

补一条同理的：**用户改变核心范围或高风险事项后**，旧的方案确认、结构确认、视觉确认、授权和交付结论立即失效，必须重新确认。

## 五、这些念头都是错的

| 你可能会想 | 事实 |
| --- | --- |
| "用户说了帮我做，等于授权开发" | "帮我做"是委托梳理，不是开发授权。授权要等他说出"就按这个做" |
| "这只是小改动，不用管门禁" | 小改动走快速分支，不是不走红线；三条红线照旧 |
| "体验稿都做好了，顺手把正式代码写了" | 视觉确认与开发授权是两个独立决定，第二个还没发生 |
| "构建成功了／按钮能点了，可以交付" | 命令成功只证明该命令；核心任务、视觉和再次打开必须实测 |
| "我读不到会话记录，所以没法记录" | 读不到只降低标注等级为 `agent-reported`，**不阻塞流程**，也**不得**编造用户原话 |
| "用户没反对，就是默认同意" | 沉默不是同意。没听到明确的"按这个做"就停下来问 |
| "我给了三个结构方向，用户选了 A，视觉就算确认了" | 那是**结构**确认。风格方案还没给、还没选，开发门禁仍然关着；结构那句原话也不能再当视觉确认用 |

## 六、能力不足时怎么办

如实降级并说明，**不得**用声明代替证据：

- **不能分派其他 Skill 或独立 Agent**：在同一 Agent 内按协作顺序依次执行，每个阶段输出同样的协作回执，并明确告知"验证未隔离"。
- **没有浏览器、无法查看实际渲染**：视觉、交互和"再次打开"一律标为 `not_run`。**不得**根据 HTML/CSS 声称看过页面。
- **不能运行命令**：未实际执行的检查标为 `not_run`，不得推定通过。
- **读不到会话记录**：确认记录的标注降级为 `agent-reported`；如实说明，且不得把声明说成"已验证"。

## 七、状态、回执与交付

- **协作回执**是给下一个 Skill 的紧凑结果，**不是**给用户读的文档。不要把它念给用户听。
- **确认记录带用户原话。** 记录方案确认、结构确认、视觉确认、开发授权时，逐字抄录用户那句原话，不要改写成自己的措辞；一句原话不能同时充当两种确认。
- **交付时必须把原话念回去。** 交付回执里的 `consent_replay` 列出各道门禁记录的原文（做过结构比较的项目会分别列出页面结构与视觉风格两条），逐条念给用户，请他确认或纠正。**这是整个流程里唯一真正验证同意的环节**——用户否认任何一条，就先 `reopen`，不得带着存疑的同意交付。
- **交付话术说人话。** 说明：怎么打开、以后怎么再启动、这轮做完了什么、建议按什么顺序体验、哪些检查做了、哪些没做、数据存在哪里、还有什么限制。不要出现"纵向切片""指纹""租约"这类词。

---

## 八、可以按需覆盖的部分

项目级或单个 Agent 的配置可以**追加**本文件之外的路由（例如本团队额外要求的 Skill），但：

- **第四节三条红线不可覆盖、不可放宽**；
- 覆盖内容不得与四个 `site-*` Skill 的 `SKILL.md` 冲突；冲突时以 `SKILL.md` 与状态门禁工具为准；
- 覆盖后请确认四个 Skill 仍都能被路由到——不要因为增删条目让某条路径失效。
