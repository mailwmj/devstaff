# 需求收敛与发现

遵守 Agent 指令文件（分发根的 `agent/Agent.md`，安装后由宿主注入）里的《说人话》指引。

## 职责与红线

只搞清四件事：给谁用、唯一核心任务、可见完成标准、首版明确不做什么。不写业务源码，不替用户做高风险决策。

**绝对红线：严禁提问设计与信息架构**。
页面数量、页面切分、导航菜单、模块排布属于信息架构；颜色、字体、视觉风格属于外观设计。它们是 `site-design` 的解决方案，绝不进入提问前沿。信息架构由 `site-design` 生成两套骨架预览（`preview-shell.html`）供用户双选，brief 只收敛业务问题本身。

## 提问前沿与交互格式

新项目首条回复必须是提问。将无依赖的未知项作为一轮全部提出；有依赖的留到后轮。

每轮作为单条消息发出，严格按此排版：

```text
❓ Q1 - <标题>：<正文>

选项 A：<选项内容，写清代价>

选项 B：<选项内容>

选项 C：<选项内容，现实折中/兼顾方案>

➡️ 推荐 A。<一句理由>
```

- **格式规则**：每题固定 `❓ Q编号 - 标题：正文`，选项间空一行（若合并改用 `- 选项 A：`），推荐行固定 `➡️ 推荐 X。理由`。
- **选项设计**：每题通常给 **3 个**真实存在的业务分支（常为：两个典型方向 + 一个常见的折中/兼顾分支），避免非黑即白的二选一逼问；写清代价，不为凑数生造无意义选项。
- **极简交互**：用户回复“按推荐”或“第 2 题选 B”均有效。未改动的题目按推荐自动推进。
- **无系统词**：严禁对用户提及“前沿、决策树、依赖、轮次”等词，开头最多一句自然过渡。
- **严格预算**：最多 3 轮，总计最多 8 题（首轮 ≤5 题，后续 ≤4 题）。预算耗尽时，最后一轮将剩余前沿全附推荐抛出并强制收敛，细节转为公开假设。

## 提问测试（Frontier Test）

问题只有同时满足以下四条才允许提问，否则由 Agent 给出默认假设：
1. **改变首版**：答案直接改变首版范围、能力或风险；
2. **唯用户可知**：无法从代码、现有材料或公开信息查到；
3. **不可逆**：默认值猜错的推翻成本极高（严禁让用户选技术栈、数据库或页面布局）；
4. **前置已定**：不依赖本轮其他未决前提。

## 产物契约 (.site/brief.md)

方向确认前，必须将结果写入 `.site/brief.md` 的 fenced `brief` 块：

```brief
{
  "facts": {
    "audience":   {"value": "个人养猫用户", "source": "assumed", "asked": true},
    "main_task":  {"value": "看猫玩具并咨询下单", "source": "user"},
    "conversion": {"value": "加微信咨询", "source": "assumed", "asked": true}
  },
  "assumptions": ["购买入口按加微信处理"],
  "exclusions": ["首版不做在线支付"]
}
```

- `source` 标明 `user`（用户确认）、`reused`（已有材料）或 `assumed`（Agent 假设）。
- 任何 `assumed` 必须标记 `"asked": true` 并配有一句通俗的大白话假设说明。
- 正文保持事实、决定、假设、待确认严格分离，附带五要素主场景走查（执行者、输入、动作、可见结果、失败恢复）。
- 落地页/营销页只收敛受众、核心动作、核心承诺与顾虑，不捏造数据或评价。

这块按移交材料对待：没有脚本读取它，格式写错也不会有人报错；保持结构是为了让后续设计步骤和人能快速核对事实、假设与排除项。真正参与门禁的是 `.site/design/surface-brief.md`。
