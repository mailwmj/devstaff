# 回答一个问题的可见实验

体验稿是用低成本成果回答一个明确问题，不是提前开发半个产品。开始前至少知道核心用户、场景、首版任务与范围、代表内容、主要设备和会改变结构的高风险边界；否则调用 `site-brief`。新建或重大改版先读 [设计上下文](design-context.md) 形成简短方向合同；已有成熟规范和局部修改只记录当前任务与例外。

## 1. 选择实验类型

| 未决问题 | 成果 | 记录方式 |
| --- | --- | --- |
| 页面如何组织，什么最重要，内容如何表达 | 结构方向（可能多个候选） | `confirm-structure` |
| 同一结构下的整体气质、排版、色彩、边界、密度 | 风格方案（默认 2 个候选） | `confirm-visual` |
| 操作按什么顺序，哪些状态可达，规则是否合理 | 流程/状态体验稿 | 业务决定交回 `site-brief` |

一个体验稿只承担一个主要问题。若外观和流程都不确定，先用最便宜、最阻塞后续决定的实验回答当前问题，再决定是否需要第二个。

**“结构方向”和“风格方案”是两件事，不是一件事的两种叫法。** 前者决定页面怎么组织，后者决定同一个页面长什么样。把两者合成一步，用户拿到的就是“结构可以，但没得挑风格”的半成品——这不是完成，是中途停下。阅读本文件时请把这两个词当作互不替代的术语。

## 2. 先结构方向，再风格方案

两步都要做，顺序不能颠倒，也不能只做第一步。

### 第一步：结构方向

默认只做一个接近成品的推荐核心页面并用 `--structure-directions 1` 声明。只有不同结构会实质改变主任务、信息优先级或高风险取舍时，才做两个足以比较的结构；第三个只在它能回答另一个重要问题时出现。**在 `confirm-concept` 里用 `--structure-directions N` 声明本轮让用户比较几个结构：只给一个结构就写 1。**不声明时门禁按“比较过多个结构”处理（fail-closed），会拦住视觉确认——忘记声明只会让你停下来补记，不会把结构选择当成风格选择。先写出该类别最容易出现的无依据默认，以及当前项目事实要求的替代答案；不能把“海报感、杂志感、科技感、粗野风”等现成风格标签本身当作方向。多个方向必须：

- 使用相同业务内容、状态和相近视口；
- 各自围绕一个清楚的结构问题，在信息拓扑、内容顺序、主要操作、密度、强调或交互模型上真正不同；
- 统一字体和颜色后，仍能解释各方向的结构差异和取舍；
- 至少指出一个来自真实业务对象、内容或行为的项目特定表现；它可以是熟悉模式的针对性用法，不要求装饰猎奇；
- 每个只做到足以判断，不扩展全部页面和完整交互；
- 已有工程时读取真实导航、组件、内容和密度，但成果写到项目旁的临时目录或明确标记的隔离体验目录，不替换正式路由和源码；由 `site-builder` 应用选中答案。

多方向可在同一个隔离体验入口使用 `?direction=a|b|c` 和轻量固定切换条。切换器明显区别于页面设计，支持分享和重新打开；确认后从正式实现删除切换器和落选方向。

**用户选定结构后，先记录结构决定，不要记成视觉确认。** 用 `confirm-structure` 逐字抄录用户那句选择（例如“结构就按 A 吧”）。这一步之后的状态是“结构已确认、风格待选”：`structure_confirmed=true`、`visual_confirmed=false`，开发仍被挡住。把结构那句原话拿去调 `confirm-visual` 会被门禁拒绝——它已经确认过结构了。

### 第二步：风格方案（选了结构就必须做）

固定已选结构、同一组真实内容、状态和主要操作，默认只提供两个完整页面风格方案；第三个只有在能回答新的重要取舍、且不增加无意义认知负担时才加入。方案使用普通人能理解的名称和描述，把内部的母题转述为可见做法（例如“每天用沿途地标作为顶部主视觉”），不以“母题：”等内部字段或 recipe、palette、typography、token 作面向用户的标签。视觉候选保持信息架构不变，让用户只比较整体气质、排版、色彩、边界、密度和素材表达。交互和状态图标默认使用 Lucide；如果使用 CDN、项目内资源或内嵌 SVG，要固定同一套图标来源，CDN 使用固定完整版本地址而非 `latest`，并单独声明离线是否成立。每个候选说明来自哪些上下文证据、突出什么、牺牲什么，并先给出一个推荐项；用户可以选择、混合、按推荐继续，或返回修改页面结构。

**候选从哪来、怎么算真正不同**，按 [内置设计工具链](design-toolchain.md) 查询并按 [视觉方向](visual-direction.md) 推导；检索无验证命中或需要中文命名时再读 [风格词汇](style-vocabulary.md)。每个候选都要有匹配依据、自己的母题、视觉世界、字体角色和构图命题，并在**母题层**不同，不是在配色层不同。填完候选后必须做**交换检查**：把任意两个候选的配色和字体互换，如果差异基本消失，它们就是同一个方向的两种上色，回到上一步重新推导。风格标签可用于命名，但不能脱离项目证据单独产生候选；搜索首条、配方目录的相邻选项、同一母题的三种强度或随机大胆款都不是新方向。

先说明一点：如果本轮在方案里就声明不需要视觉方案（`confirm-concept --no-visual`），结构与风格两步都不发生——没有任何视觉决定要记录，那属于范围判定，不是下面的例外。

第二步不是可选项。只有两种情况可以不另做候选，且每一种都要在 `confirm-visual` 里留下对应的原话：

- 用户明确委托（“你挑一个”“你决定”）：把委托那句记进 `confirm-visual`，不要替用户编一句选择；
- 已有成熟设计系统或明确参考且用户接受沿用：沿用现成视觉，仍要 `confirm-visual` 记录沿用的依据。

用户选定风格后用 `confirm-visual` 记录那句原话。同一句原话不能同时充当结构确认和视觉确认，两道记录在交付时会分别念回给用户核对。

## 3. 流程或状态体验稿

当谈论不足以判断操作顺序、状态转换或业务规则时，制作一个非技术用户可操作的轻量演示：

1. 顶部用一句话说明要回答的问题；
2. 用业务语言显示完整相关状态，不只展示原始 JSON；
3. 提供少量自由操作，让用户按任意顺序尝试；
4. 提供 2～3 个引导场景：正常流程、关键边界、应被阻止的操作；
5. 每次操作后显示发生了什么和当前状态。

默认状态留在内存，使用真实或明确标注的示例内容。不连接正式数据库，不实现登录、支付或真实外部写入；除非这些本身就是需要验证的问题，并已获得相应授权。行业惯例不能单独增加角色、页面、状态或服务。未提供的日期、价格、规则、证明材料和联系方式应标明缺口；只在结构判断确实需要时使用清楚标注的模拟值，不能用大量模拟内容把未明确的方案伪装成完整产品。

状态演示除控件可点外，还要验证操作后的语义一致性：派生计数、筛选结果、详情与列表同步，切换对象或关闭时的未保存内容，以及取消、返回和恢复。只实现本稿问题所需状态，不因检查清单扩张首版。

## 4. 保持可丢弃

体验代码只需要可运行和可判断：不为其建立完整抽象、错误体系、持久化和测试。不得因已经写了代码就直接视为正式实现。

用户确认后，将以下结果交给 `site-brief` 记录，并在同一份 `.site/design/surface-brief.md` 中补全正式实现规格，不另写一份重复的设计说明：

```text
本稿回答的问题：
核心页面、状态与主行动：
方向来源：user_selected | reference | existing | delegated
上下文依据与匹配画像：
母题与构图命题：
选定的结构（`confirm-structure` 记录的原话）：
选定的风格（`confirm-visual` 记录的原话）：
选择及理由：
推荐项及理由：
体验稿路径：
素材来源、许可和模拟范围：
需要正式实现和验证的内容：
```

正式实现规格须覆盖页面地图、区块清单、Design Token、响应式合同、组件状态、文案台账、素材地图和 `VA-*` 视觉验收标准；具体字段见 [页面设计合同](surface-brief.md)。补全这些内部实现信息不需要创作者再确认一次，但发现新的结构、视觉或高风险决定时必须回到对应门禁。

交给 `site-builder` 进入正式开发前明确：

- **演进**：选中结构可作为起点，但需补正式规则、错误处理和验证；或
- **重写**：仅保留已确认答案，按正式工程重新实施。

## 5. 完成条件

制作完成要求成果已实际可见、目标视口已查看、模拟和缺失范围已说明、创作者知道需要反馈的问题。展示前按 [评审协议](review-protocol.md) 分别检查设计判断、任务/状态和机械问题，并按 [排版](typography.md)、[色彩与素材](color-and-material.md)、[构图与节奏](composition.md) 核对工艺层，修复主要发现后用相同条件重新渲染。视觉确认还要求用户明确选择或已有适用委托；文件存在、等待超时和“挺好看”都不算开发授权。

本轮让用户比较过多个结构时，“完成”包含**两个**已记录的确认：结构那句和风格那句。只有一个时，回执是 `structure_confirmed`（结构已确认、风格待选），不是 `visual_confirmed`，也不是 `draft_ready`。
